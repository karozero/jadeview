# Cinematic movement, dynamics, and grounding

## Source path

For the animation mode whose low nibble is `0`, Iris `ANI_PlayGameObjectAnimation` captures the pre-animation position, plays the root-motion animation, measures the resulting position delta, restores the pre-animation position, divides the delta by elapsed time, and sends that velocity to `DYN_SetHorizontalSpeedComponent` (`external/irisEng/animation.c:1482–1642`). This is animation-driven horizontal velocity; it is not a direct per-frame position track. Mode `6` is a different branch: it restores the old position without making the mode-0 velocity call.

`DYN_SetHorizontalSpeedComponent` preserves the existing velocity component along gravity only when BasicForces are allocated and gravity is enabled; it replaces horizontal speed while retaining vertical speed. Otherwise it writes the supplied velocity directly (`external/jaded/src/libraries/ENGine/Sources/DYNamics/DYNaccess.c:216–248`; Iris equivalent `external/irisEng/dynamics.c:476–531`).

The frame order in Jaded is EVE, animation, AI, hierarchy, DYN, collision, recalage, then hierarchy again (`external/jaded/src/libraries/ENGine/Sources/ENGcall.c:230–370`). DYN integrates before collision. Under BasicForces, `DYN_CalculateSpeed` sums stream, traction, and `mass * gravity`, then applies configured friction; animation-derived speed can optionally skip friction (`DYNmain.c:45–151`). `DYN_ApplySpeed` advances position using the average old/new velocity times frame delta (`DYNmain.c:175–246`).

Grounding is a collision-system result, not a gravity-only clamp. `COL_ComputeReport` classifies a contact as ground or wall using its collision normal relative to inverse gravity and the configured wall-angle threshold, then derives a recalage vector from the contact geometry (`external/jaded/src/libraries/ENGine/Sources/COLlision/COLreport.c:658–900`). `COL_ComputeReports` applies that correction to the object position and may repeat collision detection; the collision loop is bounded to six retries, with a previous-position fallback if it cannot find a safe pose (`COLmain.cpp:1059–1205`). Later, `REC_MainCall` resolves the contact normal into slide/rebound velocity and honors flags such as no-rebound-on-ground or horizontal-grounds (`RECalage/RECdyn.c:646–790`). Thus vertical height correction and slope motion require the engine's collision reports and materials.

## What the archives provide

- A GAO with identity bit `0x4` gets a runtime DYN object. Iris initializes it with flags `65`, mass `1`, zero speed, and unbounded speed limits (`external/irisEng/gameobject.c:1460–1465`; defaults are `DYN_C_DefaultDynaFlags = 0x41`, `DYNconst.h:90`). That is an allocation/default, not a serialized gravity or contact state.
- The PC GAO `0x40` payload is design fields, not physics: Iris reads a four-byte word followed by an 88-byte `tGameObjectDesignFields` (`gameobject.c:3140–3165`; `gameobject.h:63–83`). JadeView's `ReadObjectExtensions` currently skips 92 bytes for this flag (`PcSceneLoader.Objects.cs:88–121`).
- GAO flag `0x200000` is multipart data, not DYN physics. The loader reads a count followed by either 68-byte matrices/names or 8-byte object/matrix-index links (`gameobject.c:2970–3028`; JadeView skips or queues these in `PcSceneLoader.Objects.cs:71–85`).
- The current JadeView WOW reader only resolves the two serialized world lighting references (ambient resources); it does not read a world-gravity vector (`PcWorldLightingReader.cs:5–17`). Iris `AI_EvalFunc_DYNGravitySet_C` requires an allocated BasicForces structure and writes the runtime gravity vector (`ai_dynfunctions.c:359–370`). The script/AI call that enables/configures those forces is therefore material to the result.
- The game loads collision instance/ZDx and collision-map resources through GAO references (`gameobject.c:3170–3198`). JadeView currently parses PC object geometry, but does not construct the native collision report pipeline or its game-material contact response. Render triangles cannot be treated as those contacts without evidence that the game collision map uses the same geometry and filters.

## Safe implementation boundary

The smallest source-faithful movement improvement is to keep mode-0 motion as a velocity input and integrate it only when its effective DYN state is known. Literal, resolved script calls can supply parts of that state (for example `DYNFlagsSet`, `DYNGravitySet`, friction, traction, and speed limits); unknown calls or runtime inputs must remain explicitly unresolved. A deterministic playback can then match DYN's force integration and average-speed position step for that known state.

Ground height, slopes, and collision response cannot be faithfully reconstructed from animation/root motion plus rendered scene geometry alone. The next grounded-motion step must parse the collision instances/maps and their filters/materials, then build collision reports and apply the source recalage order. Do not add a scene-specific floor height or a raycast against arbitrary render meshes: that would create a plausible-looking but non-native trajectory.

## Runtime inputs: recoverable versus runtime-only

The following is the smallest useful input split for an animated actor (including the Sally timeline under investigation). It describes source-backed capabilities, not a claim that every input is present in a cinematic archive.

| Input | Recoverable from loaded archive/timeline | Requires runtime script/AI or collision state |
| --- | --- | --- |
| Root-motion displacement per animation interval | Yes. The ANI/EVE track samples provide the animation transform; with effective clip, time, frequency, and transition known, their delta can be converted to the mode-0 horizontal velocity used by the engine. | Whether the action was actually selected at that instant, if selection depended on a live AI branch or gameplay state. |
| Animation play mode | Action-item `uc_Flag` low 3 bits are serialized; Jaded documents the low bits as animation mode and `ACT_SetAction` copies them into the active animation (`ACTstruct.h:35–48`, `ACTcompute.c:923–962`). Mode 0 is speed-from-animation, mode 6 is speed-from-DYN (`ANIstruct.h:107–113`). | AI `ANIModeSet` mutates the active animation flags at runtime (`external/irisEng/ai/ai_animationfunctions.c:226–246`; selector `0x32D3` in `ai_functions.c:724`). A serialized action mode is not proof it remains effective after AI calls. |
| Action clip frequency and action-item dynamics flags | Yes. The action item stores frequency and flag bytes; the PC action reader preserves these as `CinematicActionItem.Frequency` and `.Flags` (`src/Features/Cinematics/CinematicActionLibraryReader.cs:84–105`). Jaded applies the item frequency and maps its ignore-gravity/traction/stream bits when the action item starts (`ACTcompute.c:923–962`). | A later AI call can replace the action item or animation mode; transition phase and queued changes can depend on EVE timing/runtime condition. |
| Scripted action requests | Literal source-resolved `ACTActionSet`, `ACTActionFrameSet`, and `ACTActionFrequencySet` calls can be reported, joined with the actor's action kit, but they are requests/candidates rather than proof of a selected branch. The current inspector states this boundary (`src/Features/SceneEditor/Cinematics/EditorShell.Cinematics.ScriptActions.cs:66–77`). | Branch condition, call order when calls are event-triggered, whether the target owner is loaded/active, and current gameplay input. In Jaded, `ACT_SetAction` called during EVE deliberately queues the change for ANI to apply at the right fraction of the frame (`ACTcompute.c:673–678`). |
| DYN gravity, forces, friction, traction, speed and retained vertical velocity | Only the GAO DYN allocation/default is known from the archive; action-item ignore flags are known for decoded actions. | Effective DYN flags and gravity are initialized/changed by AI (`external/irisEng/ai/ai_dynfunctions.c:359–385`); speeds, traction, friction, streams and limits can also be set by runtime calls. The mode-0 setter retains vertical velocity only if the active DYN flags have BasicForces and gravity enabled (`DYNaccess.c:216–248`). |
| Grounding, collision response, slopes and bounce | Resource references may identify collision resources, but JadeView's scene render meshes are not equivalent evidence. | Contact normals/points, collision-map filtering, collision materials, recalage and response are calculated by COL/REC each frame (`COLreport.c:658–900`, `COLmain.cpp:1059–1205`, `RECdyn.c:646–790`). |

For this Sally movement case, an archive-driven evaluator can faithfully recover the clip's intended root displacement only after the action selection, item, and timing are resolved. It cannot infer the native final world trajectory from ANI alone: the engine converts mode-0 displacement to a horizontal speed, preserves vertical speed conditionally, integrates DYN, and only then applies collision/recalage. The 92-byte GAO extension under identity flag `0x40` is design data, not a serialized substitute for those runtime DYN/contact inputs (see `What the archives provide`).

### Smallest next implementation step

Add a generic per-owner **motion-mode trace** to the cinematic diagnostics, using data JadeView already decodes: action/item id, source clip, item frequency/flags, resolved literal action/frequency requests, and whether source evidence says mode 0 or mode 6. Preserve each value's provenance and mark effective mode as unknown after an unresolved `ANIModeSet` or conditional request. This improves diagnosis of T-pose and root-motion mismatches without pretending to simulate gravity or inventing a floor. The following bounded step can interpret only literal, owner-resolved DYN setters (flags/gravity/friction/traction/speed limits); collision parsing remains a separate prerequisite for grounded parity.

## `ANIModeSet` ABI and the `3500A927` evidence boundary

Iris registers selector `0x32D3` as `AI_EvalFunc_ANIModeSet` (`external/irisEng/ai/ai_functions.c:723–724`; JadeView's selector table maps `32D3` to the same name at `src/Features/Cinematics/Data/engine-function-selectors.json:697`). Its C-level signature is `(gameObject, animationChannelIndex, int16 mode)`. The script wrapper captures `AI_gpst_CurrentUltra` as the target, then pops the mode first and the channel index second, and passes those values in C argument order (`external/irisEng/ai/ai_animationfunctions.c:226–246`). The helper selects `animPtr[channelIndex]`, clears the low four flag bits, and stores `mode * 2` in them. The target game object is implicit in the VM context, not an explicit integer argument.

For `FF005520 / 3500A927`, the available `artifacts/camera-3500A927/FF005520-3500A927-script-graph.json` contains literal `ACTActionSet` requests to Sally `71003F5A` (including action 0 at 2.5 s and subsequent action 2/0 changes), but a text scan found no `ANIModeSet`, selector 13011 (`0x32D3`), or unresolved `EngineFunction_32D3` entry in that artifact. The updated root-trajectory report preserves the initial action-kit entries: action 2 selects clip `7100B0E9` with `Flags=0`, so its serialized action-item mode is 0 (`SpeedFromAnim`). This is stronger than the earlier action-name-only inference, but remains a static report rather than a runtime call trace; an unreported AI call could still change the effective mode.

At 2.5 s the raw event requests action 0, but the body timeline reports bridge `Action 54` using clip `7100B5A4` before it reaches action 0. Treat this as a transition bridge selected from action transition data, not as evidence that the source action kit has an ordinary action slot 54; the current audit does not expose that bridge item's raw flags, so its effective ANI mode remains unknown. This distinction matters when comparing root-motion output across that boundary.

The next parser seam is straightforward and generic: preserve each decoded action item's raw `uc_Flag` already read into `CinematicActionItem.Flags`, display its low-three-bit mode as the **serialized action-item mode**, then scan the owner's source-reachable literal calls for selector `0x32D3`. If a literal owner/channel/mode call is resolved, annotate it as a possible runtime override with its event time and branch provenance; otherwise retain “effective mode unknown” after any unmodeled callback boundary. Do not label the selected scene's mode-0/6 state as confirmed until the action-item bytes and resolved call route are both inspected.

## Collision resource wire layout and a safe reader boundary

Jaded's PC GAO reader confirms the serialized reference order after the modifier/design extension: one 32-bit key when either ZDM (`0x200`) or ZDE (`0x400`) identity is set, then one 32-bit key when ColMap (`0x100`) is set, then the name length/name (`external/jaded/src/libraries/ENGine/Sources/OBJects/OBJload.c:1311–1349`). Iris uses the same gates/order in `OBJ_ul_GameObjectCallback` (`external/irisEng/gameobject.c:3172–3194`). The first key is a **COL instance** reference (resource kind `d` in the current JadeView PC index), which links to a reusable ColSet and per-object zones. The second key is a **COL map** reference (kind `f`), which links to collision objects/COBs. The current cursor-based GAO reader already advances those references in that order (`src/Features/SceneEditor/Formats/Pc/PcSceneLoader.Objects.cs:18–23`); retain the key and identity provenance at those cursor positions instead of inferring them from the render mesh or runtime object struct.

Jaded's serialized resource layouts are read field-by-field, not by writing `sizeof(runtimeStruct)`:

| Resource | Serialized boundary and field order in Jaded |
| --- | --- |
| Instance (`d`) | First 4 bytes: ColSet key. A 4-byte record is a valid shorthand and initialization is deferred (`COLload.c:753–773`). Longer records then store `zoneCount, sharedCount, specificCount, priority` as four bytes; `zoneCount` one-byte ColSet/specific indices; `specificCount` variable specific-zone records; then 16-bit activation mask, 16-bit specific mask, 16-bit legacy/deleted field, 16-bit crossable, 16-bit flags, and `maxLOD,minLOD` bytes (`COLload.c:775–804,806–839,946–958`). Each specific zone is `flag,type,bone,design` bytes, a one-byte ColSet-zone index, a 32-bit name byte length plus that many bytes, a one-byte AI index, then type-dependent shape bytes. |
| ColSet | `zoneCount, flags` bytes; a 16-bit saved instance count (ignored/recomputed); 16-byte AI-index translation table; then `zoneCount` zones (`COLload.c:577–586,595–701`). Each zone begins with `flag,type,bone,design`, followed by 32-bit name length/name bytes, one-byte AI index, and shape payload. Box payload is two 3-float vectors (serialized max then min); sphere is center vector plus radius; cylinder is center plus radius and height. |
| ColMap (`f`) | A 4-byte record is a single COB key shorthand. Otherwise the first four bytes are `cobCount,activation,customBits1,customBits2`, followed by `cobCount` 32-bit COB keys (`COLload.c:509–547`). |
| COB | 32-bit game-material key, then `type,flags` bytes. Box/sphere/cylinder have their material index and shape payload. Triangle COB stores point count + 3-float points, face-normal count + normals, element count, then each element's triangle count/design/flags/material index and 16-bit triangle vertex indices. Proximity values and OK3 acceleration data are conditional on serialized COB flags (`COLload.c:236–472`; constants in `COLconst.h:57–68`). |
| Game-material table | 32-bit count, that many 32-bit palette IDs, then that many records of 32-bit flags, float slide, float rebound, sound byte, dummy byte, and 16-bit id. In editor-enabled Jaded builds, nonzero dummy values gate additional comment/color fields; retail readers should respect actual record length/build format rather than assume editor tails (`COLload.c:74–177`). |

For a reader in `PcSceneLoader`, all offsets should be computed from the resource record's own `(Offset, Size)` cursor. Before allocating or advancing, validate count multiplication/addition against remaining bytes and the resource end; reject unknown shape types or optional COB tails as unsupported while preserving the raw resource key. `COLInstance` parsing can stop after recording the ColSet key, selected zone indices, specific-zone descriptions, and flags; `ColMap` parsing can expose ordered COB keys and activation bits. Full static collision then needs the COB triangle/shape payload and game-material response data. The COL runtime structures contain pointers, padded fields, editor-only members, and values synthesized during load/resolve; their sizes are not wire-layout evidence.

The Iris source is an earlier/divergent serialization path that must not be merged field-for-field with Jaded without real resource fixtures. Its `COL_ul_CallBackLoadColSet` reads a `count,unknown,short,16 zone ids` header followed by compact per-element collision shapes (`external/irisEng/collision.c:10177–10240`), and its instance callback reads a ColSet key, then `zoneCount,sharedCount,elementCount,priority`, selected indices, compact inline shapes, and activation/flags (`collision.c:10243–10349`). Jaded instead separates reusable detailed ZDx definitions in ColSet from per-instance selected/shared/specific zones. The ColMap shorthand and counted-key form agree structurally between the two sources. Treat Iris as corroboration for the reference gates and some common resource concepts, but use the Jaded PC layout for a retail PC parser unless archive bytes prove a matching Iris-era variant.

The bounded parser and read-only source catalog are now implemented. The catalog resolves the serialized instance (`d`), ColSet (`e`), and map (`f`) records with the existing world-scoped resource index, retains missing/ambiguous/malformed diagnostics, and resolves an instance's ColSet in the instance record's source world. The Asset Inspector exposes these records under a separate Collision tab and explicitly labels them as source data, not viewport simulation. Synthetic checks cover world scoping, duplicate-key ambiguity, missing records, and malformed payloads.

The binary-compact Jaded reader was checked against all three currently audited retail containers: FF005520 (37 `d`, 16 `e`, 66 `f` records), FF0045A2 (53, 17, 47), and FF005833 (19, 10, 16). Every audited record decoded successfully with the explicit `JadedPc + BinaryCompact` selection; the audit payloads/logs are in `artifacts/collision-native-inputs/`. This supports the chosen wire layout for these archives, but does not prove every game version or malformed/unseen resource variant. The catalog currently summarizes decoded collision zones and COB keys. It does not parse COB geometry/materials or simulate collision, activation, grounding, or response. A native grounding evaluator still needs dynamic zone activation and per-frame COL/REC behavior; this work exposes source collision inputs without claiming gameplay parity.
