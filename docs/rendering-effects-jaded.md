# Effects and rendering notes from Jaded

Jaded's source is useful as an engine reference, but it is a pre-release / multi-platform Jade Engine tree. Treat behavior as a hypothesis for the retail BGE PC build until the matching data or runtime confirms it.

## Script command `GFX_DepthBlur`

Iris maps selector `0x3C3D` to `AI_EvalFunc_GFXDepthBlur`; the serialized signature is `INT FLOAT FLOAT`. Both Iris and Jaded pop the arguments in reverse stack order, so the call is `(OnOff, ZStart, ZEnd)`. The cinematic script inspector now decodes and displays those values. This command is distinct from `Gsp_AE_MASTER` mode 0, which is the generic after-effects controller already represented by the cinematic post-effect timeline.

Jaded's implementation dispatches to `Gsp_DepthBlur` only for PS2 and `GXI_DepthBlur` only for GameCube; the PC build's preprocessor branch has no implementation. Iris likewise consumes the three stack values and returns without a PC effect backend. Therefore JadeView records the command and its depth interval, but does not apply a guessed depth blur to the PC viewport. Archive census v3 found 17 serialized occurrences across three containers (`FF0057FD`, `FF001FBE`, `FF006B96`); occurrence counts do not prove that the associated scripts execute in retail gameplay.

Evidence: `external/irisEng/ai/ai_functions.c` selector registration and `ai_gfxfunctions.c`; `external/jaded/src/libraries/AIinterp/Sources/Functions/AIdeffct.h` signature and `AIfunctions_GFX.c` platform branches; `artifacts/cinematic-goal-audit/event-key-census-v3/archive-cinematic-census.json`.

## Particle generators (PAG)

Source: `external/jaded/src/libraries/GraphicDK/Sources/PArticleGenerator/PAGstruct.h` and `PAGstruct.c`.

- Jaded's PAG reader supports serialized versions 8–11 (plus legacy v0); JadeView's PC modifier reader now accepts v8–v11. The layouts progressively add sinusoidal drift, distance constraint, and the widened flag word. v11 serializes an emitter shape, velocity mode, generation rate, size and lifetime ranges, acceleration, friction, color, Z bounds, rotation, sinusoidal drift, and a distance constraint. `PAGstruct.h` names the parameters and flags; `PAGstruct.c` shows how they affect generation, update, sorting, and drawing.
- Emitter shapes 0–5 are point, rectangle, circle, cylinder, sphere, and box. Shape 6 emits from vertices of `PAG_tdst_Struct::pst_GO`, which scripts assign through `PAG_SetObject`; it does not default to the particle carrier geometry. `PAG_SetMatrixRef` selects the transform applied to those source vertices, falling back to the source object's absolute transform when unset. Direction modes 0–5 are 1D, 2D, 3D, radial-from-center, object-normal, and target.
- Cinematic literal `PAG_SetObject` and `PAG_SetMatrixRef` calls now bind uniquely keyed scene objects for shape-6 preview. If a source is not statically resolved, JadeView leaves the emitter mesh-only instead of guessing that its own carrier is the source. Object-normal emission uses the source vertex index; JadeView approximates the corresponding point normal from source triangles. Jaded instead calls `GEO_UseNormals` and reads the geometry's point-normal array (or a transformed-points modifier), so this remains an approximation.
- Jaded updates particle motion in 1/60-second increments and emits using a separate per-generator accumulator. JadeView now accumulates fixed 1/60-second physics steps independently from its emission remainder, reducing viewport-frame-rate dependence for acceleration, friction, and collision. The serialized base emission rate is available; runtime-added generator rates and their linked emitter transforms are not modeled. Random seeds and AI-driven activation also remain approximate.
- Jaded rotates each billboard basis with `X' = X*cos + Y*sin` and `Y' = Y*cos - X*sin`. JadeView now uses the same signs; the former opposite signs mirrored rotated particle textures. This is checked with a fixed 90-degree PAG fixture.
- PAG's `AccSpeed` flag (`0x8000`) adds the acceleration step to particle velocity during each update; the position update also includes the matching half-step displacement. JadeView now honors this flag and the source's additional velocity step when no Z-boundary branch handles the particle. Frame-rate edge cases and engine-wide pause semantics remain approximate.
- PAG `f_SinXFactor` and `f_SinYFactor` (v9–v11) add `sin(particle time × factor) × dt` to local X/Y position after the fixed simulation steps. JadeView reads these serialized values and follows that timing; `MathF.Sin` approximates Jaded's optimized sine lookup.
- A particle's birth duration is a visible, simulated phase, not a pause before simulation. `AlphaBirth` and `IncreaseBirth` interpolate opacity and size across it. JadeView now advances position during birth and applies those flags to the birth ramp.
- Z-min and Z-max collision checks include the particle's `f_SizeY` extent, and the corrected center is offset from the plane by that same half-size. The minimum-plane distance constraint is compared to squared horizontal distance from the emitter origin, matching the Jaded code path.
- The `Transparent` PAG flag affects render-pass participation and particle sorting. JadeView now routes a flagged particle mesh into the transparent draw queue even when the carrier's material layers look opaque; the material blend operation still determines the actual pixel composition. When Jaded's `ForceSortTriangle` path applies, JadeView sorts particle quads back-to-front by camera depth. `DontSortParticles` disables this reordering. This can matter for large star-shaped flares and overlapping smoke.
- `Freeze` prevents simulation updates while keeping existing particles visible; `Active` gates both rendering and updates. JadeView preserves this distinction for serialized PAG state and for timed cinematic `PAG_SetFlag` calls.
- Jaded script commands can add/delete runtime generators, change a generator's rate, set/clear PAG flag masks, change indexed float parameters/color, and replace the geometry or matrix references. The cinematic script inspector decodes those calls using Jaded's argument types and parameter indices, including the engine's 16-generator limit.
- Literal timed cinematic calls to `PAG_SetFlag`, `PAG_SetGeneratorFreq`, `PAG_Setf`, `PAG_SetColor`, and `PAG_ShiftParticles` apply to per-object preview state. `PAG_ShiftParticles` splits the current simulation interval at the event and translates particles already alive there; particles emitted afterward keep their original positions. Frequency changes for the source-initialized generator ID 1 are supported; IDs returned by runtime `PAG_AddGenerator` calls are not reconstructed. During cinematics the preview clock follows the timeline, and moving backward clears particles from the later frame. It does not replay a deterministic particle history from time zero, reconstruct callback-driven generator/object/matrix bindings, or recover skipped events after large forward seeks; those still require live script execution or fuller PAG timeline simulation.
- EVE vector arguments serialize three float words followed by `CastVector` (`0x1770`). The shared literal-call decoder preserves those float bit patterns as command arguments, and the script inspector describes `PAG_ShiftParticles` using the decoded vector. A fresh audit of `FF005833 / BF00218E` decoded 202 calls across 31 script owners and found no serialized `PAG_ShiftParticles` command in that graph; the source API's presence alone is not evidence that this cinematic invokes it.
- Scene export includes the currently rendered PAG particle frame as ordinary GLB triangles when a preview snapshot is available, and marks the node with `particleSnapshot` plus the preview time. The carrier geometry remains included, while fully transparent particle quads are omitted. This is a still snapshot: GLB does not contain the emitter, particle lifetime, or motion. For a useful export, pause playback at the desired moment and make sure the emitter is visible in the viewport so its latest preview frame has been evaluated.

## Material, texture, and lighting follow-up

Jaded keeps material blend operations, alpha-test flags, alpha source, texture stages, procedural texture generators, and lights in separate subsystems. Therefore, a pink quad, opaque smoke, a wrong-color flare, or a missing sky can share a visible symptom while having different causes. Debug them in this order:

1. Resolve the material and all texture stages for the exact geometry part.
2. Inspect blend operation, alpha test/inversion, local alpha, and whether alpha comes from texture, vertex color, or a later texture stage.
3. Check whether the source attaches a procedural generator/effect or updates it from an AI/script callback.
4. Only then tune viewport draw order or lighting approximation.

Jaded's `MAT_IsMaterialTransparent` treats a single material with `f_Opacity < 0.98` as transparent, and its setup changes that material to alpha blending. JadeView now reads this opacity for PC simple-material records, enables alpha blending at the same threshold, and multiplies sampled pixel alpha by the opacity. This is separate from a layered material's per-texture blend operations.

Jaded's `MAT_Cc_ColorOp_FullLight` supplies white RGB to the material. JadeView previously supplied white with zero alpha, which could erase a pass when alpha blending was selected. The preview now uses opaque white for that color operation; texture alpha, local alpha, and simple-material opacity still control transparency.

### Procedural textures and video/photo surfaces

Source: `external/jaded/src/libraries/GraphicDK/Sources/TEXture/TEXprocedural.h` and `TEXprocedural.c`.

- Jade registers procedural subtypes `0 Unknown`, `1 Water`, `2 Fire`, `3 Mpeg`, `4 Photo`, and `5 Plasma`. The texture system invokes each subtype's update callback once per render counter (`TEX_Procedural_Update`); a decoded descriptor by itself is not a pixel image.
- The video subtype loads a stream/media key and updates a texture through the platform video backend. The exact codec/backend depends on the target build (`BINK_VIDEO`, console-specific MPEG/XMV paths). For the installed PC retail build, JadeView uses a persistent x86 PowerShell bridge to the game's own `binkw32.dll`. Cinematic preview now links subtype-3 materials to `mpegplayer_init` owners, reads their `i_Play` and `des_o_Interrupteur` instance fields, and applies literal `OBJ_CapaSet` start/stop/toggle requests at source time. A controlled screen stays black until its first start and then samples Bink time relative to that trigger; seek recomputes state from the preceding source events. The inspector reports trigger and decoder state. This is a deterministic preview of recovered capability events, not execution of the AI callback VM: runtime switch state, saved-game gates, conditional callback execution and callback-frame latency remain unresolved. The bridge uses the installed game DLL at runtime; JadeView does not ship or copy it.
- The Photo subtype starts with an empty procedural buffer. `TEXPRO_Photo_SetMapGao` projects a four-point scene object through the active camera and initializes a timed capture; the update callback copies the camera image into the procedural texture. It therefore depends on runtime camera state and a trigger, not a standalone image file.
- Water initializes two empty wave buffers and evolves them; `TEXPRO_WaterDisrupt` injects impulses using runtime state and random values. A descriptor alone cannot determine a representative frame.
- Fire initializes empty buffers and builds frames by updating them through a palette. In this Jaded source snapshot `TEXPRO_FireDisrupt` returns before its old disturbance implementation, so its exact retail PC behavior must be checked against the target build.
- Plasma initializes noise fields and phase angles with `rand`/`fRand`, then updates the fields and palette. Those random startup values are not serialized in the descriptor.
- JadeView now reports these distinct runtime requirements instead of presenting the descriptor as a decoded texture; it does not synthesize a misleading still frame.
- The cinematic material inspector now names the subtype and states the missing runtime requirement. This makes a purple/missing monitor diagnosable as an unresolved video/photo/procedural source, but does not claim pixel-level playback parity.
- Scheduled nested EVE events now feed the existing material and particle preview state paths: resolved material enable/alpha commands and PAG color/deactivate/shift commands are applied with deduplication and reverse-seek checks (`CinematicMaterialChecks`, `CinematicParticleStateChecks`). This covers those decoded scheduled commands only; it is not execution of arbitrary AI callbacks or the full script VM.

### Diffuse colors and RLI

Source: `external/jaded/src/libraries/GraphicDK/Sources/MATerial/MATDraw.c`.

- The PC draw path assigns `ComputedColors` to `Diffuse` and `Diffuse2X`, while `RLI` and `InvertDiffuse` explicitly select `pul_RLI_Used`. These are distinct inputs; RLI should not be treated as a synonym for regular diffuse lighting.
- JadeView preserves serialized geometry point colors as the fallback tint for diffuse modes and now adds a bounded dynamic diffuse viewport pass for modeled Omni/Direct/Spot candidates. Specular response, complete RLI generation, native BV/sector filtering, and callback-driven light activation remain outside the renderer.
- Jaded's PC draw path issues an additional additive draw for `Diffuse2X` unless global 2x mode is enabled. JadeView approximates that result by doubling and clamping diffuse RGB in its single preview pass; exact global-mode and depth/pass behavior remain unmodeled.

Jaded keeps raw RLI separate from the computed diffuse buffer. `GEO_Render_InitRLI` assigns `pul_RLI_Used` to the selected instance/geometry colors before checking `UseRLI`; only the computed buffer receives destination subtraction (`GEOobject.c:4719-4839`). `MATDraw.c:268-283` selects raw RLI for `RLI`/`InvertDiffuse`, and computed colors for `Diffuse`/`Diffuse2X`. The subtraction first calls `COLOR_ul_Mul` on the packed destination, then saturates each channel with `LIGHT_SubColor`. Scaling uses seven binary fractions, returning zero at/below `.02` and the original color at/above `.98`. `DontScaleRLI` copies raw colors into the computed buffer, while `UseRLI` off clears that contribution. Sprite primitives force `UseRLI` (`GEOobject.c:5963-5969`); PAG preserves the carrier's RLI flags.

JadeView now mirrors this separation and packed subtraction before raster interpolation. The previous shader incorrectly darkened direct RLI materials and ignored the two draw-mask controls. GPU checks now distinguish raw/inverted RLI from computed diffuse, toggle `UseRLI`/`DontScaleRLI`, and verify instance-color precedence and restoration of geometry colors on the shared GPU mesh. The cinematic environment script supplies the destination/factor through its phase and attack palettes. Dynamic light accumulation, specular computation and callback-driven global overrides remain unimplemented; this verifies the supported source stages, not complete retail lighting parity.

Jaded's GL backend configures fog as linear depth fog from the light's `f_Start`/`f_End` and packed color. The global map manager sets those ranges from `des_f_fog_near`/`des_f_fog_far`, blends the attack ranges by the attack coefficient, and sets the fog light color from final palette entry 1. JadeView now applies the same linear RGB fade to objects carrying `GDI_Cul_DM_Fogged` (`0x4000`) in both cinematic playback and ordinary scene preview when the world has a parsed environment controller. This reproduces the scripted ranges and palette color; it does not emulate fog-light attenuation, non-linear fog modes, per-platform differences, or all draw-mask exceptions.

The GL and DX9 backends also select black fog for additive, subtractive, and PS2-shadow blend operations (blend IDs 5, 6, and 8). JadeView now follows that rule per material layer; without it, bright effects could be tinted by the scene fog instead of fading toward black. A GPU render check covers the additive case. `SpecialContrast` (ID 9) is named in the material format but has no implementation in these Jaded backends, so JadeView does not infer its appearance.

### Environment and lighting state flow

The Iris source snapshot exposes the BGE script side of the pipeline. `world_cycle_world_cycle()` in `external/irisEng/ai/ai_bge/ai_compiledscripts_global_mapmanager.c:6458-7535` samples the configured sun object's world Z (`OBJGetPos`, around 7049-7053), then chooses night, dawn, sunrise, day, or sunset ranges from the instance values `des_f_Z_nuit`, `des_f_Z_aurore`, `des_f_Z_lever`, and `des_f_Z_jour` (7054-7268). Those cut points and palette arrays are inputs from the environment-controller script model, not universal constants. At the phase boundaries, the function toggles light flag bit 3 on the configured sun, sets the global RLI factor from the matching `des_f_RLI_*` field, interpolates the normal and attack palettes, and changes the environment material's local alpha (7054-7268). The night-to-dawn overlay alpha is 127 at night and rises toward 254; later phases set it to 255. Attack state is not just a palette color: `f_coef_attaque` blends the ten normal/attack colors and separately blends fog near/far values (7364-7428).

The final palette has multiple consumers, not one global tint. In the same Iris function, entries 0 and 5 go to the current world's two ambient colors (7429-7433); entry 7 becomes the global RLI destination (7435); entry 1 colors the configured fog light (7441-7445); entries 3 and 8 become two constants on the environment object's material (7450-7467); entry 4 colors the sky material and water light channel 2 (7471-7480); entry 2 colors the sun light (7482-7490); and entry 6 is applied to the moon material, while a separately time-faded `c_moon_light` controls the moon light (7512-7534). These indices are confirmed by the writes in this function; they are not generic palette meanings for every material or scene. `LightSetColor_C` only changes a real light component on a game object carrying the light flag and an initialized light extension (`external/irisEng/ai/ai_lightfunctions.c:32-42`); `LightSetFlag_C` and `LightSetNearFar_C` also validate that component (`211-230`, `57-92`). The global `LightSetRLIFactor_C` and `LightSetRLIDestColor_C` instead write display-data state (`296-303`, `331-338`). Thus, a serialized `des_o_*` reference that does not resolve to the expected component cannot be repaired by changing its color math. JadeView now retains the PC WOW ambient baseline and evaluates the supported world-cycle ambient, RLI, fog and material values; dynamic per-object light-list evaluation remains separate (`PcWorldLightingReader.cs`, `CinematicWorldCyclePalette.cs`).

Jaded's render path then selects among different per-point inputs. `GEO_Render_InitRLI` takes instance/visual `dul_VertexColors` first, otherwise geometry `dul_PointColors`, applies draw-mask and blend-RLI rules, and writes the selected/adjusted colors into the computed color buffer (`external/jaded/src/libraries/GraphicDK/Sources/GEOmetric/GEOobject.c:4701-4834`). If the object has no RLI source or the current draw mask does not allow RLI, it explicitly clears that buffer; when `GDI_Cul_DM_DontScaleRLI` is set, the factor is zero, or destination is zero, it keeps the source colors unchanged. `external/jaded/src/libraries/GraphicDK/Sources/MATerial/MATDraw.c:268-282` chooses the RLI field for RLI/InvertDiffuse operations, computed colors for Diffuse/Diffuse2X, and white ambient for FullLight. This means serialized geometry point colors are not automatically the correct input for every material stage. RLI may be per-instance, geometry-owned, absent, or replaced by dynamically computed light colors.

Dynamic light color is another upstream stage. `LIGHT_SendObjectToLight` enumerates the current light list, rejects lights that do not affect the object, transforms/inverts geometry normals into object space, applies light flags and attenuation, then accumulates per-point diffuse/specular terms (`external/jaded/src/libraries/GraphicDK/Sources/LIGHT/LIGHTcompute.c:2506-2860`; Iris counterpart `external/irisEng/lights.c:582-747`). JadeView parses PC light bodies and receiver bounds, resolves selected-world candidates, reconstructs serialized receiver flags2 and bone-root actor references, and evaluates per-point diffuse math in the viewport and at the current export pose. Dynamic contribution is limited to modeled Omni/Direct/Spot lights; source callback activation, specular, sector membership, and unsupported bound shapes remain outside the preview. Diffuse surfaces can still look dark or flat when a runtime contribution is unsupported or its activation/state is not represented.

The PC light component record is small and separate from its owning GAO transform. Iris `LIGHT_p_CreateFromBuffer` reads a 28-byte body in this order: `flags:u32`, packed `color:u32`, `near:f32`, `far:f32`, `density:f32`, `i8:f32`, and referenced light GAO key (`external/irisEng/graphicsobjects/light.c:23-39`). The containing GRO record adds a 4-byte type word, so its complete 32-byte form is type `2` + body; this matches the PC graphic-reference path in JadeView, which resolves the trailing GAO key at offset 28. iristool independently reads/writes the same fields (`external/iristool/src/BFDataFileLib/BFChunkParsers/Map/GAOInnerParsers/GAOInnerParserLight.java:81-111`) and labels low-bit codes 0–4 Omni, Direct, Spot, Fog, and Add Material (`:132-149`). The numeric semantics are independently confirmed by iristool's renderer: `flags & 0x1007` case 1 calls `computeDirectionalLight`, case 2 calls `computeSpotLight`, including their specular variants (`external/iristool/src/iristool/Engine/Lights.java:646-677`). Jaded agrees: `LIGHT_Cul_LF_Direct=1`, `LIGHT_Cul_LF_Spot=2` (`LIGHTstruct.h:44-52`), and its renderer dispatches those codes to the matching algorithms (`LIGHTcompute.c:2738-2797`).

Iris's apparent naming mismatch is resolved by the algorithm bodies: despite the function identifiers, `LIGHT_SendObjectToSpot` is the directional Lambert routine (Y-axis and normal dot only; `external/irisEng/lights.c:455-510`), while `LIGHT_SendObjectToDirect` uses light position, range attenuation, and cone-angle thresholds (`:278-452`). Its dispatcher routes code 1 to the former and code 2 to the latter (`:700-735`), matching the Jaded/iristool semantic mapping. Treat low bits 1 as directional and 2 as spot; do not infer semantics from those two Iris function names. The `density`/`i8` body fields are used as sine-angle thresholds only by Iris's spot algorithm. This resolves the source-code mismatch; exact parity with the 2003 retail executable remains unverified.

The source does not light every parsed light GAO. Iris adds visual objects with GAO flag `0x10` to the world's `lightObjectsTablePF` (`world.c:153-170`), then rebuilds the display light list for each view from that table (`world.c:2574-2617`). A component must exist and have active bit `0x8`; fog type `3` configures fog separately, while non-fog records are excluded when sectorization hides their owner or light flag `0x40000000` is set. Iris's list capacity is 100 (`gdi.c:385`); Jaded initializes 256 slots and filters active lights, fog, sector-hidden owners, and its shadow-buffer condition while assembling the frame list (`external/jaded/src/libraries/GraphicDK/Sources/GDInterface/GDInterface.c:211`; `external/jaded/src/libraries/ENGine/Sources/WORld/WORrender.c:2861-2959`). During per-object evaluation, `LIGHT_l_IsNodeLighted` gates by the object's dynamic flag (`flags2 & 8`) against the light's `0x100`/`0x200` receiver bits; a non-null `lightGao` additionally requires identity with the shaded object's initial actor reference. With the caller's BV-test bit set, Iris checks a sphere/AABB overlap for type codes 0 or 2 using `ffar` (`lights.c:515-551`). Thus activation, ownership, render sector and local range are distinct gates; mere presence in the archive or scene outliner does not imply that a light contributes.

For each accepted non-add-material light, Iris lazily inverts the shaded object's world matrix, transforms the light's global matrix into object-local coordinates, and transforms/inverts geometry normals before evaluating points (`lights.c:611-680`). Omni-constant mode shifts the local light origin by the object BV center (`:656-680`). Color is then masked by flags `0x20` and `0x40` (the exact byte channels follow Iris's packed color convention); object/display attenuation multiplies the packed color unless draw-mask bit 30 or light bit `0x200000` disables it. The factor is `(127 - visual.distanceAttenuation) / 127 * (1 - display.lightAttenuationFactor)` (`:620-625,681-693`). The packed multiplier uses a lookup table with cutoff shortcuts at `<= .02` and `>= .98`; contributions use saturating per-channel `LIGHT_AddColor`, while absorb bit `0x80` subtracts via complemented saturating addition (`lights.c:49-93`).

The mode routines reveal reusable equations without proving retail parity. Iris type code 0 evaluates omni point lighting: scale near/far by the mean inverse-object scale and reject beyond far. For ordinary Lambert diffuse, the normal dot is divided by distance and, outside near, multiplied by squared-distance falloff `(far²-distance²)/(far²-near²)`; for `Paint` bit `0x10`, normal weighting is skipped and falloff instead uses linear distance `(far-distance)/(far-near)` (`lights.c:123-162,193-225`). Jaded has the same split and checks Paint before OmniConst (`LIGHTcompute.c:375-388,432-490`); OmniConst's separate bounds-center path uses squared-distance falloff and is reachable only in non-paint mode (`:454-470`). Type 1 is directional: transform the light Y axis, take `max(dot(normal, lightY), 0)`, and add/subtract the weighted packed color; it has no positional range or cone test (`:455-510`). The sign follows directly from Jaded negating the Y axis and then applying negative normal-dot, and Iris doing the same (`external/jaded/src/libraries/GraphicDK/Sources/LIGHT/LIGHTcompute.c:554-588`). Type 2 is spot: use the light position and forward hemisphere, apply near/far radial cutoff and linear range falloff, then apply inner/outer angular falloff derived from `sin(density)` and `sin(i8)` (`:278-452`). `Absorb` bit `0x80` changes additive into subtractive accumulation. Specular bit `0x1000` computes a separate color buffer before diffuse, with type-dependent range changes in Iris's dispatcher (`lights.c:695-735`); this specular input is not interchangeable with the diffuse buffer. Type 4 does not enter point-light accumulation: it selects an extra material on overlap or containment, with index/flags read from the light record (`lights.c:637-655`). JadeView has a pure source-derived evaluator and now carries its supported diffuse equations into viewport and current-pose export, with the AABB bounds gate described below. Callback-driven active-list changes, specular, and additional-material selection are not yet covered.

The geometry draw path calls the light-list evaluation only when material validation asks for diffuse/specular and the current draw mask allows lighting, then computes final vertex color/ambient (`external/irisEng/graphicsobjects/geo.c:806-815`; `external/jaded/src/libraries/GraphicDK/Sources/GEOmetric/GEOobject.c:6292-6395`). A shared per-draw computed-color buffer after source-time light activation remains the right integration seam: it must preserve raw instance/geometry RLI separately, skip unlit effect/PAG paths, and use the correct backend/type semantics. JadeView parses and attaches type-2 light components to owning scene objects, and archive audits report 24 lights in intro, 16 in decrypt, 40 in boss with zero unresolved references. The viewport has the serialized WOW ambient baseline, WOL last-header selection, and RLI/ambient rendering. GLB now evaluates that bounded RLI/ambient stage for color modes 0/6 while preserving raw vertex paint for modes 3/5. Dynamic omni/direct/spot point-light accumulation is not integrated into viewport or export, and the pure light evaluator remains a standalone math seam. Exact PC arithmetic, script-driven light toggles, and retail pixel results still require runtime capture or a matching PC build; available Iris/Jaded sources document stages and algorithms, not a verified retail frame.

Particle color follows a separate path from world ambient and diffuse lighting. Jaded writes each active particle's generator color to its four billboard vertices and modifies alpha/size during birth and death (`external/jaded/src/libraries/GraphicDK/Sources/PArticleGenerator/PAGstruct.c:1186-1265`, and sprite path 1321-1381). Before rendering the generated geometry, PAG clears `TestBackFace`, `Lighted`, and `UseAmbient` from the draw mask, then restores the saved mask (`1391-1399`). Thus the world-cycle ambient and ordinary dynamic-light terms should not be applied to PAG quads as if they were lit meshes; authored generator color and particle age flags are their base appearance. Fog may still apply if the carrier's remaining draw flags select a fog path. The Iris world-cycle's water palette write at `ai_compiledscripts_global_mapmanager.c:7471-7480` is a distinct water-renderer channel, not a generic particle tint. A flare or smoke color mismatch should therefore be traced to its PAG color, material/texture stage, and timed `PAG_SetColor`/flag calls before changing the global sun or ambient palette.

Fog also has a per-object selector. Jaded swaps between fog slot 1 and slot 2 according to `GDI_Cul_DM_UseFog2`, and only enters the fogged path for `GDI_Cul_DM_Fogged` objects (`external/jaded/src/libraries/GraphicDK/Sources/GEOmetric/GEOobject.c:5230-5235`, `6270-6274`); non-fogged materials restore their normal draw state (around 5810). JadeView currently models one world-cycle near/far/color tuple and the `Fogged` mask, but not two independent fog slots or the `UseFog2` choice (`src/Features/SceneEditor/SceneRenderer.Cinematics.cs:28-32`; `src/Features/SceneEditor/SceneRenderer.cs:284-307,1573-1574`). This can cause a scene with two fog volumes/ranges to look globally misted, insufficiently fogged, or to use the wrong color even though the first fog setup is correct.

The current system-level implementation carries literal cinematic light-state snapshots and current transforms into a per-draw candidate resolver and computed diffuse evaluator. Serialized WOW baseline, WOL merge order, world-cycle ambient channels, RLI factor/destination, selected fog/material outputs, type-2 light records, receiver flags2, initial actor references and static AABB range gating are represented. Animated GAOs with the native range-test mask are deliberately excluded because live skeleton-derived bounds are not reconstructed; arbitrary callback execution, both native fog slots, all local-alpha owners, callback-driven light activation and per-vertex specular remain absent. Explicit cinematic `OBJ_FlagInactiveSet` events now gate world-cycle controllers in preview, but GLB does not animate that state. Checks cover receiver/type gates, object-reference matching, transformed directional normals, direct position independence, omni/spot ranges, spot-cone boundaries, packed channel flags, saturation/subtraction, static AABB range and animation-bound exclusion. The Iris/Jaded source match is architectural evidence, not proof of retail PC pixel parity.

### Loaded-world light candidate discovery

JadeView now has a pure ordered candidate resolver in `src/Features/SceneEditor/Rendering/Lighting/SceneLightCandidateResolver.cs`. It takes one selected `WorldData` (including the assembled cinematic world when playing a cinematic), the current `CinematicLightStateEvaluation`, and an explicit scope. It requires the source GAO light identity flag `0x10`, a resolved non-null PC light resource, and the effective active bit at the requested playhead. It preserves `WorldData.Objects` order, routes type 3 fog separately, keeps type 4 additional-material lights out of diffuse, and classifies unknown light codes instead of passing them to the point evaluator. For diffuse and type-4 receiver candidates it applies the source receiver class (`flags2 & 8` => light flag `0x100`, otherwise `0x200`) and initial-actor reference gate. The desktop shadow-buffer bit `0x40000000` is excluded from the ordinary list. Tests cover selected-world scoping, source order, per-playhead flags, receiver/reference filters, light-type routing, sector membership and bounds-test diagnostics (`tests/ExportVerification/SceneLightCandidateResolverChecks.cs`).

The inputs to those receiver gates can now be reconstructed from the PC object model by `NativeLightReceiverContextResolver` (`src/Features/SceneEditor/Rendering/Lighting/NativeLightReceiverContext.cs`). `SceneObject.SerializedStateFlags` retains the raw GAO word at offset 12 independently of identity `Flags` and editor `ControlFlags`; the typed loader, `SceneLoader.ParseGao`, and the actor's root/bone/source-mesh construction preserve it. This mirrors Iris `OBJ_ul_GameObjectCallback`: initialize runtime flags2 from `serialized & 0x7B9C0080`, map serialized bits `0x20000000` and `0x40000000` to runtime `0x200000` and `0x400000`, preserve `serialized & 0xFF00`, then run `OBJ_UpdateStatusFlagRTL` (`external/irisEng/gameobject.c:47-70,2849-2867`). That routine sets runtime bit 3 only for identity flags with `0x4000` or `0x2`; it requires `(identityFlags & 0x26) != 0` or state bit `0x40000`, and state bit `0x80000` then forces bit 3 off. For light reference matching, Iris `LIGHT_l_IsNodeLighted` compares the light's `lightGao` against `ANI_pst_GetReferenceInit(receiver)` (`external/irisEng/lights.c:515-551`); the latter follows parent references while identity flag `0x1` (bone) remains set and returns the first non-bone ancestor (`external/irisEng/animation.c:2484-2505`). The JadeView helper performs this traversal from `ParentId`/`GaoKey`; missing, ambiguous, or cyclic bone-parent links return typed diagnostics instead of silently treating a bone as its own actor. Unit checks exercise static/dynamic receiver status, state override and flag mapping, bone-root resolution, missing/ambiguous parents, and cycles (`tests/ExportVerification/NativeLightReceiverContextChecks.cs`). This models loaded-object initialization and hierarchy only; script-mutated runtime flags2 still require a separate evaluated-state source.

This is an adapter over parsed selected-world members, not a reconstruction of Iris's live world table. Iris adds identity-light GAOs to `lightObjectsTablePF` only during visibility activation (`external/irisEng/world.c:153-169`), then rebuilds a per-view list from that table, requiring active flags, routing fog, applying the sector filter, and omitting bit-30 lights (`:2574-2617`). Jaded performs the corresponding active-world-list, fog, sector and shadow-buffer selection in `external/jaded/src/libraries/ENGine/Sources/WORld/WORrender.c:2867-2950`. The PC loader attaches each light component to its owning world member from the identity flag and resource reference (`src/Features/SceneEditor/Formats/Pc/PcSceneLoader.Objects.cs:93-115`, `PcSceneLoader.Worlds.cs:69-96`; `src/Features/SceneEditor/SceneLoader.cs:53-80`). Cinematic overrides are available from `CinematicPlayback.LightState` at the playhead (`src/Features/Cinematics/Models/CinematicPlayback.cs:175`).

The default JadeView full-world preview scope means exactly the supplied scene/assembled `WorldData`, not every WOL root parsed in the document. Native sector membership and the live visible-world light table are not represented; therefore sectorized resolution requires explicit per-object membership, and unknown/out-of-sector entries are excluded with diagnostics. Parsed PC bounds are attached to `SceneObject`. When draw-mask bit `0x200000` requests the native range test, Omni/Spot candidates are retained for static AABB or OBBox outer extents and resolved current receiver/light positions; outside candidates are excluded. Animated receivers are excluded with a typed diagnostic because the game recomputes their bounds from the current skeleton, while JadeView only has the serialized default/bind bounds. Sphere metadata remains preserved but excluded with a typed diagnostic. Static OBBox uses its outer BVMin/BVMax, matching the native AABB gate; its local corners are not inputs to that gate (see light-obb-range-audit.md). The multipart root position is applied only when the source identity condition and actor hierarchy resolve. Type-4 overlap/containment evaluation remains separate. The loader does not infer source callback activation; it consumes only the evaluated literal cinematic light-state snapshot.

#### Serialized receiver bounds and the native light-range gate

The PC GAO stores its bounds vectors at record offset `+90`, after a four-byte padding word. Without identity bit `0x00080000`, the payload is two `Vec3` values (`BVMin`, `BVMax`, 24 bytes); with that bit it is four vectors (48 bytes), adding `BVMinLocal`/`BVMaxLocal`. Iris reads the vectors after the padding word and branches on the identity flag (`external/irisEng/gameobject.c:2850,2897-2924`); the runtime `tGameObjectBV` allocation is 48 or 72 bytes including that word (`gameobject.c:1483-1496`; layout in `gameobject.h:38-49`). Jaded names `0x00080000` as `OBJ_C_IdentityFlag_OBBox` and reads two or four vectors after its dummy word (`external/jaded/src/libraries/ENGine/Sources/OBJects/OBJconst.h:37`, `OBJload.c:348-375`). iristool independently parses the same vectors and reports the full 48/72-byte struct (`external/iristool/src/BFDataFileLib/BFChunkParsers/Map/BFGaoChunk.java:808-885`). JadeView's `PcObjectBoundsReader` reads the serialized payload at `+90`, preserves both local vectors, attaches the parsed result to `SceneObject`, and supplies the static-AABB range gate described here.

The sphere marker is encoded separately: raw `BVMax.z == 0xffffffff` identifies a sphere, `BVMin` is its center and `BVMax.x` its radius (`external/irisEng/gameobject.c:92-102,244-245,273-278`; Jaded `OBJBoundingvolume.c:48-70`). It is not a special meaning of the OBBox identity flag, and the sphere check uses the first two vectors even if the extended local vectors are also present. The bounds values are loaded without a coordinate conversion. Iris's light-range test subtracts the selected receiver position from the light owner's position and tests that delta against the receiver's `BVMin`/`BVMax` with the light's far radius (`external/irisEng/lights.c:515-551`); it does not consume `BVMinLocal`/`BVMaxLocal` in this gate. The caller enables this check only when draw-mask bit `0x200000` is set (`lights.c:620-631`). Native BV allocation is controlled by the identity bit, not serialized `flags2`; the receiver gate checks for a non-null bounds pointer. `flags2` has other runtime uses, including dynamic/static receiver class and spatial/detection flags, but is not the BV-presence switch.

Serialized bounds are not valid substitutes for the current bounds of animated GAOs. Iris dispatches animated objects to `OBJ_ComputeAnimBV` (`gameobject.c:744-795`), which clears the extents, walks the current skeleton, rebuilds boxes, merges bone bounds, and saves the resulting runtime min/max each update (`gameobject.c:695-736`). JadeView therefore fails closed for a bounds-gated receiver with identity animation bit `0x2`, emitting `ReceiverDynamicBoundsUnavailable` rather than accepting/rejecting a light from stale serialized extents. Static AABB candidates use the source-derived gate; dynamic animated bounds and spheres remain outside current preview support; static OBBox outer AABBs are supported.

Receiver position is usually the GAO's world-matrix position. For multipart actors whose flags match `(flags & 0x600001) == 0x600001`, with more than one multipart element and a resolvable initial actor reference, Iris transforms the child position through the referenced root matrix before the range test (`lights.c:530-545`). Jaded has a corresponding PC path (`external/jaded/src/libraries/GraphicDK/Sources/LIGHT/LIGHTcompute.c:1145-1188`), and iristool independently applies the root adjustment (`external/iristool/src/iristool/Engine/Lights.java:509-539`). JadeView applies that source-derived adjustment for resolved multi-member actor hierarchies and exposes the root owner/matrix on the prepared plan so the outer render cache can invalidate when it moves. Do not treat the extra local corners as proof of a fully oriented-volume test: the cited native light path uses the current `BVMin`/`BVMax` values.

One implementation detail remains version-sensitive. Jaded's `INT_SphereAABBox` rejects only when a per-axis gap exceeds the sphere radius (strict `>`), accepting tangent contact (`external/jaded/src/libraries/ENGine/Sources/INTersection/INTmain.cpp:219-288`). The available Iris decompilation has a suspicious Y-branch and early-return pattern in its corresponding routine (`external/irisEng/collision.c:5462-5500`), so exact retail 2003 behavior should not be claimed from Jaded alone. Regression fixtures cover just-outside, exact grazing, inside, unsupported sphere/dynamic OBBox, static OBBox outer extents, missing bounds, and multipart-root selection (`tests/ExportVerification/SceneLightCandidateResolverChecks.cs`, `SceneObjectDiffuseLightingChecks.cs`). A retail/runtime capture is still needed to confirm these cases against the shipped PC game.

### Implemented world ambient baseline and world-cycle channels

PC `.wow` v3 serializes ambient 1 before the 60-byte world name and ambient 2 after the matrix, FOV and clear color. This is confirmed by iristool's `BFWOWChunk.parse` (`external/iristool/src/BFDataFileLib/BFChunkParsers/Map/BFWOWChunk.java:134-162,194-221`) and used by JadeView's bounded PC reader at payload offsets 12 and 152 (`src/Features/SceneEditor/Formats/Pc/PcWorldLightingReader.cs:5-16`). Iris reads the same two values while constructing a world; ambient 2 value `-1` means reuse ambient 1 (`external/irisEng/world.c:1223-1254`). JadeView retains this baseline in `WorldData.Lighting`; for a WOL merge chain, `SceneLoader` preserves the listed WOW order, and the assembler chooses the last parsed world header, matching Iris's sequential world merge (`world.c:2796-2833,1418-1427`) and iristool (`BFWOLParser.java:443-512`). This is chain-scoped: an unrelated resident/basic world is not an ambient source unless the WOL chain includes it.

The supported world-cycle preview can then override that baseline with palette entry 0 as ambient 1 and entry 5 as ambient 2, including attack palettes and animated sun height (`external/irisEng/ai/ai_bge/ai_compiledscripts_global_mapmanager.c:7428-7433`). Capability 256 suppresses those controller writes, in which case the serialized baseline remains available. Each evaluation reconstructs the values for backward seeking. This follows the existing environment-controller preview route, not arbitrary AI callback execution. Archive audits now report the resolved header, including boss `62000D52 = FF4D431F/FC605424`, home `100045A7 = 006F624A/00685844`, and decrypt `D90057CC = FF61516B/FC645454` (`artifacts/black-material-audit/boss-focus.log`, `house.log`, `pipes-focus.log`).

The vertex shader adds ambient RGB after computed diffuse/RLI subtraction, clamps channels, and preserves alpha, following `LIGHT_ComputeVertexColor` and the x86 saturating-add path (`external/jaded/src/libraries/GraphicDK/Sources/LIGHT/LIGHTcompute.c:3030-3058`; `LIGHTcolor.c:211-270`). `UseAmbient` gates addition; `DontUseAmbient2` selects channel 1 instead of channel 2. Direct RLI/InvertDiffuse and FullLight retain their own inputs. PAG draw passes clear `UseAmbient`/`Lighted` as the source does. Viewport checks cover ambient selection, saturation, and RLI isolation (`tests/ExportVerification/CinematicMaterialChecks.cs:134-165`; `CinematicMaterialRenderChecks.cs:300-339`). Dynamic diffuse is wired into the viewport and current-pose GLB sample for modeled Omni/Direct/Spot candidates; limits and viewport runtime evidence are listed below. GLB remains static and does not animate light changes or glTF material properties.

### Per-object lighting, material layer order, and current coverage

The source separates object draw policy from world lighting. `GRO_tdst_Visu::ul_DrawMask` is copied into the active draw state before geometry rendering; its bits independently gate RLI (`GDI_Cul_DM_UseRLI`, `0x40`), ambient (`UseAmbient`, `0x100`), fog (`Fogged`, `0x4000`, with `UseFog2`, `0x10000000` selecting the alternate fog state), and dynamic per-object lighting (`Lighted`, `0x08000000`). The definitions are in `external/jaded/src/libraries/GraphicDK/Sources/GDInterface/GDInterface.h:42-85`; the renderer applies the visual's fog selection before `GEO_Render_SubObject` and the material/RLI work in `GEOobject.c:6269-6304`. These are draw-time conditions, not proof that a cinematic script has activated a light or effect. A script can change world/light/material state, while the visual draw mask determines whether an object consumes each channel.

For the retail-style software path in Jaded, the order is: resolve an RLI source, optionally compute dynamic diffuse/specular, combine ambient into computed vertex color when requested, then draw the material's texture levels. `GEO_Render_InitRLI` resolves instance/visual colors before geometry-owned colors (`GEOobject.c:4676-4734`). When RLI is enabled it may blend a second RLI field or apply the destination subtraction; when no usable RLI is enabled it clears the computed buffer (`4701-4834`). For diffuse/specular materials, `GEOobject.c:6292-6395` sends the object to the light list only when `Lighted` is set, then calls `LIGHT_ComputeVertexColor`. `LIGHT_SendObjectToLight` tests each current light against the object and accumulates point diffuse/specular (`LIGHT/LIGHTcompute.c:2506-2860`). The final color stage adds world ambient only under `UseAmbient`; `DontUseAmbient2` selects `ul_AmbientColor` instead of `ul_AmbientColor2` (`2970-3058`). Therefore ambient and dynamic light do not replace/override RLI globally: the material's validation/color operation decides which computed buffer it consumes, and draw-mask bits determine which calculations are enabled.

Material colors are selected for each linked texture level, not once per object. In the PC `MATDraw.c:247-300` path, `Diffuse`/`Diffuse2X` select `ComputedColors`, `RLI` selects `pul_RLI_Used`, `InvertDiffuse` selects RLI with an RGB XOR, `Specular` selects the specular buffer when available, `Disable` uses the material's packed constant, and `FullLight` supplies white. `UseLocalAlpha` applies that level's serialized local alpha through the packed color XOR. The renderer then calls `GDI_SetTextureBlending` with that level's own flags, computes UVs, and draws the geometry (`334-386`). A `Diffuse2X` level receives a second additive draw when global 2x mode is off (`387-400`). `MATmultitexture.c:738-803` confirms levels independently contribute validation requirements: alpha blend/alpha test may require RLI alpha unless local alpha supplies it. Thus texture alpha, selected color-field alpha, local alpha, alpha test and blend operation are separate inputs; later levels can composite over earlier levels. Jaded's exact back-end blending is platform-specific, so this ordering is source-confirmed but not automatically retail-PC pixel parity.

JadeView now carries the modeled diffuse stage into the viewport, but not the whole stage graph:

- `SceneLoader` stores per-object `RliColors` and draw flags (`src/Features/SceneEditor/SceneLoader.cs:530-531`); geometry point colors are packed into GPU vertex attributes (`SceneRenderer.cs:559-575`). `UpdateInstanceAlpha` selects instance RLI by vertex index before geometry color and uploads both packed color and alpha (`1208-1231`), so instance RGB is represented as well as alpha. This is an object-specific override over the cached geometry paint, not a computed light result.
- The shader applies quantized RLI destination subtraction in `SceneRenderer.cs:254-260`; its fragment stage chooses material color mode and optional instance alpha (`292-304`). Current tests cover the packed subtraction and several synthetic material-color cases in `tests/ExportVerification/CinematicMaterialRenderChecks.cs:81-245`. Those are deterministic GPU fixtures, not a captured retail object/material fixture.
- `SceneRenderer.Lighting.cs` builds per-object candidate plans in selected-world source order, derives runtime receiver flags and initial actor reference, reads the current game-space object/light transforms, and evaluates packed diffuse for the current skinned vertex buffers. The GPU tangent channel carries computed RGBA while the raw RLI channel remains unchanged. The plan cache keys the source-state signature and owner/pose/appearance state; a prepared plan avoids per-vertex matrix inversion and world scans. The overlay toggle can disable this viewport pass. This implementation supports modeled diffuse Omni/Direct/Spot lights and an AABB range gate when draw-mask bit `0x200000` requests it; sphere and animated-bounds receivers are explicitly excluded, and native sector culling is still unsupported. Captured timed light setters and modeled world-cycle sun/fog fields are consumed, while arbitrary callback-driven activation, moon runtime state, specular, type-4 additional materials, cylindrical spotlights, and exclusive-light modes remain unsupported. Unknown source/device attenuation defaults to zero. GLB export captures supported dynamic diffuse at the current source pose, plus RLI/ambient for color modes 0/6; modes 3/5 preserve raw paint.
- Material-level preview is a reduced mapping: it handles supported color modes, local/override alpha, alpha test, blend modes, opacity, and selected fog behavior, but it does not execute the fixed-function multi-texture combiner as an arbitrary sequence of per-level source/destination operations. `Diffuse2X` is represented as a clamped doubled tint in one pass rather than Jaded's extra additive draw. Exact ordering and alpha result for stacked stages remain an implementation gap.
- PAG colors are distinct: Jaded writes generator color to billboard vertices and clears `Lighted`/`UseAmbient` for particle drawing, so ordinary mesh ambient/dynamic diffuse must not be applied to those quads (`PAGstruct.c:1186-1265,1391-1399`).

GPU regression tests now cover direct/omni diffuse, raw-color isolation, timed light flags, and static plan reuse (`tests/ExportVerification/DynamicLightRenderChecks.cs`; `SceneObjectDiffuseLightingChecks.cs`). An actual viewport performance capture for intro `3500B8EA` at 23.68–25.68 s recorded 120 frames at 960x540 over 2.02 s, 5.59 ms average render time, 27.31 ms max frame, and no frames above 33.33 ms (`artifacts/light-component-integration/dynamic-av-intro.log`). This verifies the current editor path and cost, not retail pixel parity. The intro remains an archive-driven investigation target; a retail PC pixel/region capture with the same clip, camera, time and object state is still needed for a visual golden.

3. **Current bounded math slice:** the pure batch evaluator implements Omni, Direct and Spot diffuse color contribution over explicit current vertices and caller-supplied light state. ### Backend blending, alpha test, and activation boundary

The available GL and DX9 implementations confirm most fixed-function blend equations, but they are not perfectly identical. The GL backend configures alpha test with strict `GL_GREATER` (or `GL_LESS` when inverted), using the serialized threshold divided by 256; it independently enables/disables the test, applies color-write masks, sets depth compare/write, and maps local alpha into the current vertex-color OR mask (`external/jaded/src/libraries/GraphicDK/Sources/backends/gl/OGLinit.cpp:1922-1967`). DX9 uses the same strict greater/less comparison and the same threshold accessor, plus equivalent write/depth setup (`external/jaded/src/libraries/GraphicDK/Sources/backends/dx9/DX9blending.c:34-56,86-121`). `MAT_Cul_Flag_AlphaTest`, `InvertAlpha`, `HideAlpha`, `HideColor`, `ZEqual`, `NoZWrite`, `UseLocalAlpha`, and `InActive` are distinct flags in `MATstruct.h:31-45`; alpha test is not the same as alpha blending.

For both available backends, Copy/Glow disable blending; ordinary alpha uses source-alpha / inverse-source-alpha; premultiplied alpha uses one / inverse-source-alpha; Add uses one / one; and Sub/PSX2 shadow uses zero / inverse-source-color (`OGLinit.cpp:1979-2048`, `DX9blending.c:124-199`). InvertAlpha swaps/changes relevant factors in both. A source-confirmed exception is the destination-alpha modes: GL `AlphaDest` uses `(DST_ALPHA, ONE_MINUS_DST_ALPHA)` and DX9 uses `(INVDESTALPHA, DESTALPHA)`; their premultiplied forms also differ (`OGLinit.cpp:2005-2019`, `DX9blending.c:158-184`). This is a real backend source divergence; without retail-PC capture it must not be normalized away or declared a bug. Blend-state changes are cached against the previous mode in each backend, so a faithful evaluator must apply every level's state transition, not only the final material flags.

Texture-level ordering is the material's linked-level traversal: the PC `MATDraw` loop selects color/alpha state, sets blending for the current level and draws it, then advances `pst_NextLevel` (`MATDraw.c:198-244,247-300,334-407`). Per-level color op, blend op, alpha-test threshold/inversion, local-alpha, and UV state are stored in the flags/level record (`MATstruct.h:31-98`). `MAT_Validate` separately marks whether a level needs diffuse, specular, RLI, constant or full-light computation and whether alpha requires RLI (`MATmultitexture.c:749-803`). At object scope, transparent materials may be queued into the Z list before the main pass (`GEOobject.c:6100-6113`); exact ordering across all render queues and platforms still depends on the selected backend and runtime state.

The scripting source proves why a serialized material/effect can be present yet not visible in a preview. Iris `world_cycle_world_cycle` conditionally toggles the configured sun's light flag bit 3 as the sun height crosses phase thresholds, and writes RLI factor/palette values as part of that same phase update (`external/irisEng/ai/ai_bge/ai_compiledscripts_global_mapmanager.c:7045-7070,7100-7143`). It then writes ambient, global RLI destination, fog-light color and material constants (`7428-7480`); this is direct source evidence that scene appearance is runtime-mutated state. Other compiled callbacks set up light ranges/flags and target references, e.g. `SFX_Disapear_dis_init` (`external/irisEng/ai/ai_bge/ai_compiledscripts_sfx_disapear.c:25-49`). Effect scripts also configure a GFX instance's material and parameters, then call `GFXFlagSet` for specific flag indices (`external/irisEng/ai/ai_bge/ai_compiledscripts_actor_cv_aircraft.c:551-591`). Jaded invokes an object's `AI_C_Callback_BeforeDisplay` from the object render path (including the AI referenced by a bone) before drawing it (`external/jaded/src/libraries/GraphicDK/Sources/GEOmetric/GEOobject.c:6116-6149`). Thus activation can be a per-frame callback side effect, not just a one-time EVE event or a property inferable from asset presence.

The static boundary is now explicit. **Covered from available sources:** the above software-path RLI source precedence and packed arithmetic; draw-mask gating; dynamic-light/ambient inputs; material color-op selection; linked layer traversal; GL and DX9 blend/alpha-test equations, including the known destination-alpha divergence; the Iris world-cycle palette writes; examples of Iris light/GFX mutations; and Jaded's pre-display callback hook. These conclusions describe the checked-in Jaded/Iris code paths, not automatically retail behavior.

**Still unverified for retail BGE PC:** which Jaded branch/backend and compile-time switches correspond to the 2003 retail executable; the retail meaning and native execution details of every GFX flag index and GFX callback; callback ordering relative to cinematic messages and script conditions in the retail runtime; which object light lists and visual draw masks are active at a given retail frame; and whether the GL/DX9 destination-alpha divergence exists in the game's actual PC path. Resolving these requires either retail runtime instrumentation/capture or a matched executable/source build; the checked-in reverse-engineered Iris calls and Jaded engine source alone cannot answer them.

Material UV scrolling is evaluated against cinematic playhead time while a cinematic material state is active, so seeking or replaying now reproduces the same scroll position. Ordinary scene preview still uses elapsed editor time. This synchronizes the serialized scroll transform; it does not recreate texture-video frames or all script-driven UV changes.

JadeView's current particle preview keeps the carrier material and geometry association. It does not reproduce Jaded's complete fixed-function multi-stage material state or the retail game's dynamic effect/script state. The GLB exporter captures a frozen cinematic layer snapshot, applies timed enable/alpha/threshold/environment and per-object local-alpha values before disabled-layer filtering and baking, and computes supported RLI/ambient plus modeled dynamic diffuse at the selected pose; raw color modes 3/5 remain authored. Export fixtures cover computed `COLOR_0`, ambient/raw channels, frozen-time capture and disabled layers. It does not animate glTF materials or lights, calculate specular output, or provide full material-stage parity.

GLB export captures the editor's evaluated `CinematicMaterialLayerSnapshot` before traversing source material layers. It applies playhead-time layer enablement, alpha, alpha threshold, environment color, and per-object local alpha before filtering disabled layers and baking the material. A fully disabled material retains its named node without a fallback mesh material. The exporter computes packed RLI subtraction and ambient RGB for supported color modes 0 and 6, then captures modeled Omni/Direct/Spot diffuse at the selected source pose; raw modes 3 and 5 keep authored vertex color. Supported layer compositions are tinted during baking, including third-overlay destination masking, with local alpha applied once. `CinematicMaterialExportChecks`, `ComputedColorExportChecks`, and dynamic-light fixtures cover frozen-time capture, `COLOR_0`, ambient/raw-color modes and modeled light output. Export is still a static sample: glTF material/light animation, specular light and full material-stage parity are not implemented.

### Desktop backend and sky/water render routes

The checked-in Jaded build selects OpenGL in the graphics interface. `GDInterface.c` includes the OGL interface (`external/jaded/src/libraries/GraphicDK/Sources/GDInterface/GDInterface.c:34-36`), labels `GDI_gi_GDIType` as OpenGL (`81`), and initializes the function-pointer table with `M_INITGDI(..., OGL)` regardless of the `_l_GDIType` argument (`405-429`). Its GraphicDK CMake target compiles the GL implementation (`external/jaded/src/libraries/GraphicDK/CMakeLists.txt:236-254`) while the DX9 source list is commented out (`209-234`); the executable links `OpenGL32` (`external/jaded/src/main/CMakeLists.txt:499-503`). DX9 files remain useful evidence for alternate blend semantics, but they are not the backend selected by this Jaded build. The many `SOFT_*` helpers in `GDInterface` are CPU-side geometry, matrix, picking, and ordering support; they do not establish a software rasterizer as the desktop renderer. The similarly named `SOFTbackgroundimage.c` is compiled only under `ACTIVE_EDITORS` (`external/jaded/src/libraries/GraphicDK/Sources/SOFT/SOFTbackgroundimage.c:11`), and its screen-image setup is explicitly called an editor-only special case (`GDInterface.c:1433-1434`). It is not evidence of the in-game sky route.

This does **not** identify the retail BGE 2003 PC backend. Jaded describes itself as a community-patched fork of source from around May/June 2006 (`external/jaded/readme.md:13-15`), and its current CMake build is a later Windows/x86 project (`readme.md:43-50`). Iris contains BGE-specific script calls, but these checked-in sources do not connect the retail executable to Jaded's current OpenGL selection. Treat the retail PC API, driver path, and compile-time switches as unknown until directly observed or matched to the retail binary.

The source separates at least three things that can be mistaken for “the sky/water.” First, the Iris map-manager enables a global water/ocean subsystem only when `WTR_activation` is set, then sends sky/bottom/water colors, wave and tiling values, speed, direction, propagation, and water height through `WTR_SetL/F` (`external/irisEng/ai/ai_bge/ai_compiledscripts_global_mapmanager.c:2130-2148,2251`). Iris `world_cycle_world_cycle` also writes its current sky palette color to the sky object's material constant and to water light slot 2 (`...global_mapmanager.c:7469-7480`). The script-side calls are real state updates: Jaded's AI interpreter writes indexed fields into `stExportWaterParrams` and calls `WTR_SetExportParams` (`external/jaded/src/libraries/AIinterp/Sources/Functions/AIfunctions_mth.c:1946-1987`). `LINKstruct_reg.cpp:2886-2902` names the indexed fields: sky/bottom/water colors, mesh size, spectrum powers, cloud-shading toggle, texture reference, wave height/choppiness/tiling/speed/water height/direction/propagation.

Second, Jaded has a distinct global ocean mesh generator in `TEX_mesh.c`: it stores sky/bottom/water colors and water height in `WTR_Generator_Struct`, initializes spectrum state (`external/jaded/src/libraries/GraphicDK/Sources/TEXture/TEX_mesh.c:320-378`), accepts the script-export structure and updates/reinitializes the global wave spectrum (`431-461,540-603`), and computes a camera-frustum mesh using FFT displacement (`1669-1873,2336-2389`). `TEX_mesh_x86.c` contains a separate x86 renderer, but its source entry is commented out in the current GraphicDK CMake list (`external/jaded/src/libraries/GraphicDK/CMakeLists.txt:197-203`). In this checkout, `WTR_Mesh_Do` has no caller outside its own source file, and the x86 renderer has no external call site in the checked-in sources. Therefore the parameter/state pipeline is statically traceable, but whether this ocean mesh is active in the current Jaded executable, which rendering hook invokes it, and whether it corresponds to retail BGE water remain unproven.

Third, `TEXPRO_Water` is a procedural animated texture, not the ocean surface mesh. Its load callback allocates two zeroed wave buffers and builds a palette; its update callback evolves the height buffers and writes palette colors into the texture buffer; its disrupt callback injects randomized impulses (`external/jaded/src/libraries/GraphicDK/Sources/TEXture/TEXprocedural.c:363-448,455-508,514-561`). The procedural dispatcher calls disrupt/update once per display-data rendering counter and uploads the result (`TEXprocedural.c:2095-2129`). A static decoded texture cannot reproduce that evolving image without the runtime state, including impulses and update timing. `GFX_Water2` is yet another mechanism: it emits transient expanding/fading colored quads/rings with per-instance position, normal, size, duration, and color, then draws them with material 0 and back-face testing disabled (`GFX/GFXwater.c:181-267,274-340`; parameter names in `GFX/GFX.h:403-415`). It is an effect primitive, not evidence of the ocean implementation.

The practical implication for JadeView is to keep these routes distinct. A sky object whose constant changes should be evaluated through that object's material chain and activation state; global water colors/parameters belong to the WTR subsystem; a water-typed procedural texture needs deterministic source-time buffer simulation and script impulses; water rings belong to the GFX effect timeline. The editor background image is not a substitute for any of them. This gives a generic diagnosis for missing/incorrect sky, water, and “sun glow” visuals without claiming that any screenshot's bright sprite is a native sun: its actual object, material, draw flags, alpha/blend mode, and activation must be identified from the scene data.

**Closed from available static sources:** current Jaded desktop build selects GL and excludes its listed DX9 implementation; shared `SOFT_*` names do not establish software rasterization; editor background image is an editor-only facility; Iris world-cycle sky constants and WTR parameter writes; water/ocean exported parameter names and FFT mesh generation; procedural water texture update/impulse route; and transient `GFX_Water2` geometry behavior.

**Still requiring runtime or retail-binary evidence:** which graphics API the BGE 2003 retail PC executable actually uses; whether the checked-in Jaded ocean mesh is invoked by an active render path and how it maps to the retail water; when retail callbacks enable WTR or inject procedural/GFX disturbances; the exact sky object's scene/material assignment and render flags for affected clips; and which glow/portal/sun effects are active at a given source time. A useful verification capture must pair a retail clip/time and camera with the active object/visual, material-level chain, WTR/GFX/procedural state, and representative pixels.
