# World universe script state

This note and the reducer describe a small shared engine-script state slice. It is not a cinematic playback feature: cinematics are one possible source of literal commands, while ordinary object scripts and gameplay can call the same engine functions.

## Source behavior

- `external/irisEng/ai/ai_functions.c:169-174` registers selectors `0x1F40` (`WORUniverseAdd`), `0x1F41` (`WORActive`), `0x1F42` (`WORDesactive`) and `0x1F46` (`WORLoadList`). The current selector catalog is also in `src/Features/Cinematics/Data/engine-function-selectors.json:142-147`.
- `external/irisEng/ai/ai_worldfunctions.c:24-39` shows that `WORUniverseAdd` consumes one world key, invokes `WOR_pst_Universe_AddWorld(key, 0, 1)`, and returns that world's universe-table index.
- `external/irisEng/world.c:1283-1300` first checks the archive-address cache when loading a world. If the world is already loaded, the cached pointer is reused. `external/irisEng/world.c:2243-2261` initializes the loaded world, rebuilds its **object-activation** table when requested, and adds the world pointer to the universe table only if that pointer is not already present. So adding a world already in the table returns its original slot rather than creating another entry.
- In Jaded, `external/jaded/src/libraries/ENGine/Sources/WORld/WORuniverse.c:715-742` has the same load/init/rebuild sequence and pointer-identity duplicate check before table insertion. Its AI wrapper at `external/jaded/src/libraries/AIinterp/Sources/Functions/AIfunctions_wor.c:687-703` returns the table index.
- Iris `WORActive` at `external/irisEng/ai/ai_worldfunctions.c:43-55` sets bit `1` in the selected **universe-table slot** and updates the current-world pointer. `WORDesactive` at lines `58-66` clears that bit and does not update the current-world pointer. Jaded wrappers are at `AIfunctions_wor.c:737-759`; the corresponding flag helpers are `external/jaded/src/libraries/ENGine/Sources/WORld/WORaccess.h:95-140`.
- `WORUniverseDestroy` is selector `0x1F45` (`ai_functions.c:172`) and consumes a universe slot plus a second ignored integer in Iris (`ai_worldfunctions.c:84-97`). It destroys the referenced world and removes its universe-table entry when destruction succeeds (`external/irisEng/world.c:342-347`). Jaded's `WOR_Universe_DeleteWorld` likewise removes the pointer from the table after successful destruction (`external/jaded/src/libraries/ENGine/Sources/WORld/WORuniverse.c:862-883`). Since that can affect slots and the current-world reference, the reducer invalidates its projection rather than trying to preserve later slot indices.
- Iris `WORLoadList` at `ai_worldfunctions.c:100-119` calls `WOR_pst_Universe_AddWorldList` with a world-list key. This is a different resource/operation from adding one world key, and is intentionally not reduced here.

## Separate runtime concepts

`WORUniverseAdd` rebuilding the world's active-object table does not set the world's universe-slot active bit. Object activation is a different scheduler: Jaded `WOR_World_ActivateObjects` (`external/jaded/src/libraries/ENGine/Sources/WORld/WORmain.c:166-190`) rebuilds the per-world active-object table and calls `WOR_ActivateObjectIfFlagsAllow`. Visibility uses another table and predicate in `WOR_World_MakeObjectsVisible` / `WOR_MakeObjectVisibleIfFlagsAllow` (`WORmain.c:102-164,198-225`). The reducer only projects universe slot order, per-slot active bits, and the current-world reference. It does not infer object activation, visibility, sector state, or callbacks from those values.

## Current bounded behavior

`GameWorldUniverseReducer` accepts an explicit initial ordered slot snapshot (including known holes), literal integer calls, and a set of archive world keys already resolved by the caller. It can model:

- adding a resolved world key to a known universe order;
- returning the existing slot when that world is already present;
- activating/deactivating a known slot and preserving the source's current-world pointer behavior;
- reporting unresolved world keys, unknown initial slot order, invalid slot indices, and unsupported `WORLoadList` without inventing state. Unknown mutating operations invalidate the slot/current-world projection, so later numeric slot calls cannot silently apply to a stale universe.

It does not open archives, execute AI, create worlds, read world-list resources, reduce `WORUniverseDestroy`, or execute object activation/visibility callbacks. The PC Iris table appender (`external/irisEng/tables.c:444-455`) compacts holes if the slot array is full before appending. Since capacity is not in this reducer's input, adding a new world while known holes remain is reported unresolved instead of guessing whether the slots will shift. A production adapter needs to supply an ordered loaded-universe snapshot and resolved world-key set; if those inputs are unavailable, the result stays unknown instead of guessing.

## WOL roots are merge inputs, not universe slots

The PC FF0 header and `PcSceneLoader.ReadWorldRoots` contain an ordered sequence of `(world key, ".wow")` entries. This matches iristool's WOL parser (`external/iristool/src/BFDataFileLib/BFChunkParsers/Map/BFWOLParser.java:376-417`), and the runtime Iris loader reads 8-byte key/value entries from the supplied list resource (`external/irisEng/world.c:2796-2830`). Iris skips zero and `0xFFFFFFFF` keys and merges each remaining WOW into one destination world. The first merge creates/registers the destination; later keys merge into that same world. At the end it assigns the list key to `world->worldKey`, rebuilds the merged world's object activation table, and assigns that one world as current (`world.c:2843-2860`). Thus the ordered `replay.Worlds`/`WorldData` roots describe world membership and merge order; they are not one universe slot per root.

The slot index after `WORLoadList` is not recoverable from the WOL header alone. Iris deletes the old worlds by removing entries from the existing PF table (`world.c:2734-2741,339-347`) but does not reinitialize that table. Its module init starts with capacity four (`world.c:250-253`). Table removal can leave holes or shorten only the trailing edge (`tables.c:364-393`); appending writes at `nextElemPtr` and compacts holes only when the table is full (`tables.c:444-455`). The new merged world is inserted through `WOR_pst_Universe_AddWorld` with slot flags zero (`world.c:2243-2261`). Therefore both prior table layout/capacity and the exact call history matter for numeric slots, even though the merge member order is known. This is why a list load invalidates the current reducer's slot projection.

JadeView currently preserves decoded roots in `PcSceneLoader.ReadWorldRoots` (`src/Features/SceneEditor/Formats/Pc/PcSceneLoader.Worlds.cs:31-48`), reads each root into `Result.Worlds` in header order (`PcSceneLoader.Resources.cs:78-92`), then turns each record into a separate UI `WorldData` (`src/Features/SceneEditor/SceneLoader.cs:48-96`). That layout is useful for editing and source-world diagnostics; it is not an engine universe snapshot. The existing `artifacts/camera-3500A927/FF005520-3500A927-script-graph.json` reports 13 `LoadedWorlds` entries (basic actor libraries, map, cinematic root, and subscene), but that field is serialized directly from `document.Worlds` (`tests/ExportVerification/CinematicScriptGraphAudit.cs:631`), not raw header bytes or a runtime table capture. It must not be interpreted as observed universe slot order.

The next adapter seam is to retain a `PcWorldListDescriptor` at parse time: the outer archive entry/list key plus the raw ordered header keys, including zero/invalid placeholders. `SceneLoader.Load(Archive, Entry)` has the entry key, but `PcSceneLoader.Read` currently receives only bytes and archive path, and `ReadWorldRoots` keeps its list local. A `WORLoadList` projection can then report the merged logical world key and ordered member keys from that descriptor. It still must return an unknown numeric slot unless the caller also supplies the pre-transition PF-table layout (including holes and capacity) or a runtime/script history that establishes it. Do not synthesize initial slots from `document.Worlds`, cinematic assembly order, or the selected subscene key; a scene being opened is not evidence that its WOL list was executed as `WORLoadList`.
