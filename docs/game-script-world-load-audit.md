# World-list loading in game scripts

This note follows selector `0x1F46` from the AI function table through the Iris and Jaded world loaders, then compares that behavior with JadeView's serialized WOL parsing. Iris is the closest available PC-oriented source model, but it is not a retail BGE executable trace. Jaded and iristool provide corroboration for the WOL layout and related engine design, not proof that every detail is identical in the shipped PC game.

## Script ABI and return value

- Iris registers selector `0x1F46` as `AI_EvalFunc_WORLoadList` alongside `0x1F40` `WORUniverseAdd` and `0x1F41`/`0x1F42` active-state operations (`external/irisEng/ai/ai_functions.c:169-175`). JadeView's selector catalog maps `1F46` to the same operation (`src/Features/Cinematics/Data/engine-function-selectors.json:142-147`).
- The Iris wrapper pops one integer key, calls `WOR_pst_Universe_AddWorldList(0, worldKey, 0)`, looks up the resulting world pointer in the universe table, and pushes the index (`external/irisEng/ai/ai_worldfunctions.c:100-119`). It does not branch on a null result before the index lookup. The underlying pointer lookup returns the table's pointer index (`external/irisEng/world.c:349-352`); what a failed index means to each compiled caller is not established here.
- Jaded's function declaration independently names the operation `WOR_LoadList`, takes one `INT`, returns `TYPE_INT`, and binds it to `AI_EvalFunc_WORLoadList_C(int)` (`external/jaded/src/libraries/AIinterp/Sources/Functions/AIdeffct.h:213`). Its wrapper likewise pops one integer, pushes the returned index, and advances the node (`external/jaded/src/libraries/AIinterp/Sources/Functions/AIfunctions_wor.c:637-646`). This supports the signature, not retail PC implementation identity.

## Iris load-list state transition

`WOR_pst_Universe_AddWorldList` (`external/irisEng/world.c:2705-2868`) is a world replacement path, not an additive asset request. In source order it:

1. Stores the requested outer key, begins load hooks, marks the first post-load frame, clears groups, and initializes the result to null (`2728-2732`).
2. Deletes every currently loaded universe world (`2734-2741`), detaches the display, then resets graphics, sound, text, texture, input, and photo/global state (`2742-2780`). These destructive steps occur before its explicit `worldKey == -1` early return (`2781-2782`).
3. In Iris's demo/read-mode-2 branch, checks for a companion key formed with `worldKey | 0xff000000`; the explicit missing/same-key cases return null (`2784-2793`). This is a source-specific guard, not a generic retail-PC error contract.
4. Reads the WOL resource as 8-byte records: a 32-bit key and a second 32-bit value (`2796-2808`). It determines the first and last non-placeholder keys (`2813-2821`), skips `0` and `0xffffffff`, and merges each remaining world root into a single destination world (`2823-2834`).
5. Ends speed loading; if no world resulted, disables temporary memory and returns null (`2837-2842`). Therefore an empty list or a list containing only skipped placeholder keys has no merged world in this implementation. The wrapper's response to null is the table lookup described above.
6. Assigns the outer list key to the merged world, resolves AI references, clears the main actor pointer, activates the merged world's eligible objects, rebuilds its EOT table, assigns it as `currentWorld`, and attaches the display (`2843-2862`).

Iris rounds the WOL byte size down to complete 8-byte records (`size >> 3`, `2799-2808`) and does not visibly validate a trailing partial record in this function. `iristool` instead rejects lengths not divisible by eight (`external/iristool/src/BFDataFileLib/BFChunkParsers/Map/BFWOLParser.java:376-383`). A missing archive key is not shown to have a clean error path in Iris: this function passes `BIG_ul_SearchKeyToPos(worldKey)` into `BIG_pc_ReadFileTmp` (`2784-2797`). Do not represent malformed/missing-key behavior as a confirmed retail result without a runtime trace.

## Separate meanings of add, object activation, and active-world selection

The world loader has two distinct levels of state:

- **Per-world object activation.** `WOR_pst_Universe_AddWorld` loads and initializes a world, then when `resolveAI` is true calls `WOR_World_ActivateObjects` and builds its EOT table (`external/irisEng/world.c:2243-2262`). The PC Iris object predicate uses `flags2` and special-time state to decide which GAOs enter the activated-object table (`external/irisEng/world.c:44-62`). The list loader performs the same object-resolution/activation work after merging (`world.c:2852-2858`).
- **Universe-slot active flag/current-world pointer.** `WORUniverseAdd` inserts a newly-seen world pointer with slot flags `0` (`world.c:2258-2259`); it does not set that slot's active bit. `WORActive(slot)` sets bit `1` in that slot and recomputes `currentWorld` from the active table (`external/irisEng/ai/ai_worldfunctions.c:43-55`); `WORDesactive(slot)` clears that bit and does not update the pointer (`58-65`). The active-world lookup scans from the supplied slot forward for the first loaded entry with bit `1` (`external/irisEng/world.c:354-366`).

Jaded corroborates the distinction: its `WORUniverseAdd` calls world load/init, rebuilds the per-world activated-object table when requested, and inserts a new universe slot with flags `0` (`external/jaded/src/libraries/ENGine/Sources/WORld/WORuniverse.c:715-744`). `WOR_World_ActivateObjects` rebuilds the separate `st_ActivObjects` table from all world objects and applies the object activation predicate (`external/jaded/src/libraries/ENGine/Sources/WORld/WORmain.c:166-190`). The universe active bit is a separate bitfield helper (`external/jaded/src/libraries/ENGine/Sources/WORld/WORaccess.h:95-140`) used by Jaded's `WOR_Activate` wrapper (`external/jaded/src/libraries/AIinterp/Sources/Functions/AIfunctions_wor.c:737-749`).

**Accuracy note for the existing JadeView description:** `GameScriptWorldOperationDescriptions` currently says `WORUniverseAdd` “loads a world, initializes it, resolves and activates its objects, and adds it to the universe” (`src/Features/GameScript/GameScriptWorldOperationDescriptions.cs:15`). That is accurate. It does not claim the universe slot itself becomes active. The reducer test name was clarified to `VerifyAddDoesNotActivateUniverseSlotOrSelectCurrentWorld`; its distinction is consistent with the source. The `WORActive` description at line 16 is also accurate for a valid loaded slot, with the source nuance that the current-world lookup searches from that slot onward.

## Jaded and iristool comparison

Jaded's loader reads each WOL entry as `(world key, 32-bit type)` and derives entry count from `ul_Size >> 3` (`external/jaded/src/libraries/ENGine/Sources/WORld/WORuniverse.c:480-490`). It skips keys `0` and `0xffffffff`, selects first/last real members, and merges each remaining world in order (`493-519`). It catches loader errors into a null world (`522-524`) and on failure returns null after cleanup (`536-551`). On success it assigns the outer WOL key (`554-555`), resolves references, activates objects, rebuilds EOT, and attaches the result (`621-654`). The Jaded AI wrapper performs additional fixed-world resolution/reentrant loads before the normal list load (`AIfunctions_wor.c:591-609`), and a platform/custom-main-menu key rewrite (`618-626`). These are not established for retail PC Iris, so JadeView should not port those branches without target-version evidence.

iristool's WOL parser expects 8-byte entries, reads a key and four-character `.wow` marker, permits key zero without the marker, and retains the ordered keys (`BFWOLParser.java:376-418`). This agrees with JadeView's typed PC reader, which accepts `.wow` records or the zero placeholder and preserves serialized order (`src/Features/SceneEditor/Formats/Pc/PcSceneLoader.Worlds.cs:32-50`). JadeView stores these roots as `GameWorldListDescriptor(outerListKey, orderedWorldRootKeys)` and explicitly preserves zero/`0xffffffff` placeholders (`src/Features/GameScript/Models/GameWorldListDescriptor.cs:3-19`). The descriptor is archive metadata, not a capture of runtime universe slots or proof that a script invoked `WORLoadList`.

## What archive script evidence establishes

The decoded archive graph for `FF001FBE` / cinematic `35009F74` contains four `WORRefreshVisible(0)` calls in camera-special handlers; sampled graphs for `BF00218E`, `BF003BD1`, and `3500B8EA` contain no decoded `WORLoadList`, `WORUniverseAdd`, or `WORUniverseDestroy` calls (`docs/gameplay-script-system-findings.md:900-908`). This is evidence about those decoded graphs only. It neither proves a retail runtime world load nor excludes another owner, external gameplay state, or an unrepresented/undecoded function path.

## Keyed WOL resolution in JadeView

The cinematic script inspector now resolves a literal `WORLoadList(key)` against that keyed archive resource. `PcWorldListHeaderReader` is shared with the normal PC scene loader, so both paths use the same length bounds, 8-byte entries, `.wow` marker / zero-placeholder rule, and serialized ordering. The inspector reports the WOL resource name and ordered roots, including placeholders; it does not attach those roots to the current cinematic or execute the command. `GameScriptWorldListArchiveReader` reports missing keys, duplicate keys, invalid PC WOL payloads, and bounded-read failures distinctly. Results are cached per archive and WOL key.

Validation against the installed retail archive resolved `FF005833` to `ff005833.bin` and read 12 serialized roots, including `BF000127` and `8F00384A`; the same parser is used by the scene loader. `A9003274` resolved to the PS2 resource `PSX2_au_taquet.wol`, which was correctly rejected as non-PC instead of being mistaken for a PC world list. The focused regression fixture covers ordered roots, zero/`0xffffffff` placeholders, the outer-list identity, consumed header bytes, truncated input, invalid tags and invalid lengths. The archive probe can be repeated with `--pc-world-list-resource-audit <archive> <hex-key>`.

This is still static resource association. Do not map roots to universe slots, claim a command ran in game, attach every referenced root to the selected cinematic, or infer active-world state. Numeric return slot requires prior PF-table layout/history; execution requires the callback/trigger path and runtime conditions, which this passive archive join does not provide. The reducer may continue to invalidate its projected runtime universe state when it encounters the unsupported load operation (`src/Features/GameScript/GameWorldUniverseReducer.cs`).

This work does not execute `WORLoadList` or alter scene playback. A future runtime-backed reducer would need, at minimum, pre-transition universe slots including holes/capacity, a confirmed world-list resource resolution, and a trustworthy indication that the command was dispatched; absent any of these, the slot/current-world outcome remains unknown.

## Selected cinematic fixtures: archive roots are not runtime universe state

I checked the saved PC graph audits for `FF005833 / BF00218E` and `FF0045A2 / 3500B8EA`. Their `LoadedWorlds` arrays are copied from `SceneDocument.Worlds` (`tests/ExportVerification/CinematicScriptGraphAudit.cs:631`), and contain 12 and 14 archive-loaded world records respectively. Those arrays do not carry universe-slot indices, slot flags, runtime insertion order, current-world pointer, or `ENG_gf_SpecialTime`. The graph JSON schemas likewise contain no runtime universe snapshot. `FF005833` includes `_basic_*` libraries, `00_02_home_decryptage_cine` (`BF000127`), `Carte3D_Home` (`8F00384A`), and gameplay `00_02_home_decryptage` (`D90057CC`); `FF0045A2` includes the corresponding cinematic `3500B8E7`, `Carte3D_Home`, `ENV_SpiralDomz`, and gameplay intro `10001ED5`. These are archive membership facts only.

Neither graph's direct decoded clip-track commands contain `WORLoadList`, `WORUniverseAdd`, `WORActive`, `WORDesactive`, or `WORPlayAbsTime`. Their embedded EVE list counts (10 and 13) describe references, not runtime dispatch. The intro graph does contain source-reachable `WORCurIndexGet`, `WORPause`, and `WORUnPause` references; this still does not prove those callbacks ran. `WORCurIndexGet` returns an engine universe index, and the static graph does not resolve that runtime integer back to a slot or world key. This agrees with the sampled-graph limitation already recorded in `docs/gameplay-script-system-findings.md:900-908`.

`ENG_gf_SpecialTime` cannot be reconstructed from these archives either. Iris shows that `WORPlayAbsTime_C` writes both special-time globals (`external/irisEng/ai/ai_worldfunctions.c:338-350`), the object activation predicate branches on whether special time is zero (`external/irisEng/world.c:44-62`), and the engine clears the special-time values after its special-time step (`external/irisEng/engine.c:583-594`). Those sources explain what state would mean if the command ran; they do not establish its initial value or dispatch history for either retail-PC cinematic. The lack of a decoded call in these graph audits is not evidence that no other owner, external gameplay callback, or earlier game state set it.

There is one real WOL verification artifact, `artifacts/world-list-real-verification.json`, but it is for outer list `FF005520` and explicitly labels its roots “not the runtime universe slot table.” It is not the WOL for either selected home/intro graph, so it cannot fill their missing state. More generally, the PC loader stores a WOL's ordered roots as `GameWorldListDescriptor` (`src/Features/SceneEditor/Formats/Pc/PcSceneLoader.Worlds.cs:4-12,32-48`; `src/Features/GameScript/Models/GameWorldListDescriptor.cs:4-19`); it does not decode universe slots. The graph audit loads its container without a WOL key (`tests/ExportVerification/CinematicScriptGraphAudit.cs:10`), and emits loaded archive worlds rather than an executed load sequence (`:631`).

**Result and safe next step:** for both fixtures, universe slot order, active-slot flags, current world, and special-time value/history remain `Unknown`. Do not derive them from WOL root order or from the `LoadedWorlds` array. A useful next evidence source is a source-confirmed caller chain that establishes which WOL is loaded and the subsequent `WORUniverseAdd`/`WORActive` operations for the retail scene transition; if that call chain is not available, a runtime capture of the universe table and special-time globals at cinematic entry is required. Until then the existing reducer should keep these fields unknown unless given an explicit state snapshot, rather than manufacturing a predicted cinematic state.

## Startup and transition call chain in the available engine sources

Iris does expose a partial startup chain. `main.c:20-29` calls `ENG_InitApplication`, opens the BF, initializes the engine, then enters `ENG_Loop`. `ENG_InitApplication` initializes AI and the world module (`external/irisEng/engine.c:809-834`); `WOR_InitModule -> WOR_Universe_Init` zeroes the universe structure and initializes an empty world table (`external/irisEng/world.c:250-258`). `ENG_InitEngine` marks the initial reload state (`engine.c:779-788`). On the first frame, `s_InitBeforeTrame` handles that state by calling `AI_Reset` and `WOR_Universe_Open(BIG_gst.hdr.startKey)` (`engine.c:617-633`). `WOR_Universe_Open` loads the universe AI instance from the BF start key, while `AI_pst_LoadInstance` performs resource load, reference resolution, and `AI_ReinitInstance` (`world.c:2511-2517`; `ai_common.c:1441-1454`). For the local `sally_clean.bf`, the BIG header parser reads `startKey` at `external/irisEng/bigfiles.c:627-642`; a read-only header check returned `71003FF9`.

That chain initializes an empty universe and loads its global AI instance; it does **not** statically load the selected scene or produce a world-slot snapshot. During frames, the engine runs the global AI instance when enabled (`engine.c:528-534`) and then processes world-table entries whose active flag is set (`engine.c:540-578`). Calls such as `WORLoadList`, `WORUniverseAdd`, and `WORActive` are registered AI selectors (`external/irisEng/ai/ai_functions.c:169-175`); their wrappers call the world loader or change slot state (`ai_worldfunctions.c:24-65,100-119`). The supplied Iris source has no direct C call site from `main` to these world-transition wrappers: the missing edge is the serialized global/script execution and its runtime branch conditions, not the wrapper implementation.

Iris source also confirms why a WOL cannot supply the returned slot number. `WOR_pst_Universe_AddWorldList` removes existing worlds, merges WOL roots, and the first successful root goes through `WOR_pst_Universe_AddWorld` (`world.c:2734-2741,2823-2834,2679-2698,2243-2261`). That first root creates one merged world-table entry; later roots merge into that same world. The wrapper returns the table index found by pointer (`ai_worldfunctions.c:100-119`; `world.c:349-352`). It does not assign one slot per WOL root. More importantly, PF-table removal can leave interior holes (`tables.c:364-391`), insertion appends at `nextElemPtr` (`tables.c:444-455`), and the table manager may compact holes later (`tables.c:328-360,488-493`). Thus an exact index depends on prior slot occupancy and compaction timing. Even the reset-style list load cannot be assigned a numeric slot from WOL order alone. A separate `WORActive(slot)` call sets the slot's active flag and updates current-world selection (`ai_worldfunctions.c:43-55`); loading a list and selecting an active slot are distinct state transitions.

`ENG_gf_SpecialTime` is also a runtime state, not a serialized scene field. The `WORPlayAbsTime` callback writes it and `ENG_gf_SpecialDT` (`ai_worldfunctions.c:338-350`); engine stepping consumes that state and clears it after the special-time interval (`engine.c:495-594`). The compiled `global_mapmanager` callback changes the time while scrubbing a paused map/video and sends `f_abstime` with a `1/6` time step (`external/irisEng/ai/ai_bge/ai_compiledscripts_global_mapmanager.c:5581,5634,5722`). This is concrete evidence that the globals can be changed by later script/input history, not an initial value encoded in either cinematic BF. A cold process may begin with zero-initialized C globals, but that does not tell us their values when a cinematic is entered after gameplay or menu activity.

Jaded corroborates the same broad split—`WOR_Universe_Init` clears the universe table (`external/jaded/src/libraries/ENGine/Sources/WORld/WORinit.c:111-115`), and `WOR_Universe_Open` loads only the universe AI instance (`:141-150`)—but its source tree contains no application call site for `WOR_Universe_Open`; the game/application driver is outside that checkout. Its `WOR_LoadList` implementation also has fixed-world preloading and a custom-level rewrite branch before it reaches `WOR_pst_Universe_AddWorldList` (`external/jaded/src/libraries/AIinterp/Sources/Functions/AIfunctions_wor.c:560-634`). Those branches make Jaded a corroborating engine model, not a source of retail PC transition history.

**Safe integration boundary:** a source-derived startup model can describe `UniverseInitializedEmpty` and `StartAiResourceRequested(startKey)` for the Iris branch. It must leave loaded worlds, slot indices/flags, current world, and special-time state unknown until a decoded owner callback/selector is proven dispatched with its inputs. For PC archives, WOL roots can describe the merge set/order only. To predict actual state, the remaining evidence is either the retail/global AI instance plus a complete execution path through its startup and transition callbacks, or a runtime snapshot of the universe table and special-time globals; neither is present in these cinematic graph fixtures. No production behavior should be inferred from the Iris/Jaded source difference alone.

## All-world archive index: coverage is not transition history

I checked `artifacts/goal-audit/archive-gameplay-script-index.json`, whose scope is `all worlds` and whose summary reports 196 indexed worlds, 15,950 resolved script owners, 435 unique script models, and 300 `TopFunctions` entries. Its owner summaries retain container, owner, brain, world, model, and event-resource keys; its model/function summaries provide callback-key mapping and aggregate owner/container counts. The JSON has no ordered callback-dispatch trace, selector-call edges, universe-slot snapshots, current-world key, or special-time samples. Searching the index for the world-transition API names (`WORLoadList`, `WORUniverseAdd`, `WORActive`, `WORDesactive`, `WORPlayAbsTime`) returns no call records; that is expected from this schema, not proof that the scripts never invoke them. The function names in the index identify mapped callback implementations, not the commands those callbacks execute.

This all-world census therefore improves owner/model coverage but does not close the startup edge identified above. Recovering transition history from static content would require resolving and executing the global startup callback chain (including branch conditions, messages, and callback timing), and then following its world-loading selectors in order. The current archive index is a resource/callback inventory; the compact OFC metadata and source-key mappings do not expose those executable node bodies or a dispatch trace. Until a decoded execution path or runtime capture exists, initial slot order, selected world, and `ENG_gf_SpecialTime` at a particular scene remain unknown even when every world and owner is indexed.

## Global-AI startup inventory in JadeView

`Archive.StartKey` now reads the serialized BIG header startup key at offset 40; `StartEntry` resolves it only when the FAT contains exactly one matching entry. `ArchiveStartupScriptReader` follows the instance's model and instance-variable references, then resolves `.ova`/`.ofc` entries from the model's typed eight-byte reference records. The Script Inspector exposes this as **BF global AI startup resources**, separate from per-world cinematic owners, because the global AI is not a scene owner.

The reader accepts a trailing partial model-reference tail without assigning it meaning: Iris iterates `size >> 3`, so any incomplete bytes are ignored by that source implementation. For the installed `sally_clean.bf`, the inventory resolves start key `71003FF9` (`univers.oin`), model `71003FF3` (`univers.omd`), instance variables `71003FF8` (`univers.ova`), one model-variable descriptor, and seven OFCs including `univ_init.ofc`, `univ_go.ofc`, `univ_exec_get_world_key.ofc`, and `univ_exec_load_new_world.ofc`; 4 trailing model bytes are reported but left uninterpreted. Verification command `--archive-startup-script-audit` writes the same static inventory to `artifacts/export-verification/archive-startup-script-inventory.json`.

This improves resource discoverability only. The panel does not run callbacks, evaluate `JumpFalseSP`, or claim that a scene is active. The known source chain shows `univ_init` handing its callback track to `univ_go`; runtime global variables still select whether to load a WOL, which world key is supplied, what slot index is returned, and when `WORActive` is reached. See `docs/game-script-global-ai-startup-audit-agent.md` for raw-node and Iris/Jaded references.

**Safe next integration boundary:** expose the archive census as coverage metadata only, and keep runtime universe fields explicitly unknown unless supplied by a trace/snapshot. Do not translate world-script count, owner count, callback-name prevalence, or WOL root order into a predicted transition sequence.

## Archive-wide reachable world-transition call audit

To go beyond the metadata-only index, `tests/ExportVerification/ArchiveWorldTransitionCallAudit.cs` adds CLI command `--archive-world-transition-call-audit <archive>`. Each match records container/world/owner, callback roots and reachable callback path, API variant, raw source arguments and assignment evidence, branch conditions, source file and line. Every record is labeled `reachable source callsite; not runtime dispatch`; container load failures are reported separately rather than hidden.

Run on the local `sally_clean.bf`: `C:\Program Files\dotnet\dotnet.exe run --project tests/ExportVerification/ExportVerification.csproj -- --archive-world-transition-call-audit "E:\SteamLibrary\steamapps\common\Beyond Good and Evil\sally_clean.bf"`. I cross-checked two existing cinematic graph audits against their `ReachableScriptOwners` keys. `FF005833 / BF00218E` had zero matching transition callsites among its reachable owners. `FF0045A2 / 3500B8EA` had 18: freeze/unfreeze and pause helpers, plus `WORCurIndexGet` from helper-text and environment-cycle callbacks. The result is consistent with Iris's source: the wrappers are registered selectors (`external/irisEng/ai/ai_functions.c:169-175`), while actual dispatch belongs to callback/runtime state; source reachability alone does not reconstruct transition history.

The report is written to `artifacts/export-verification/archive-world-transition-call-audit.json`. It is a static evidence inventory, not a VM, execution trace, or proof that a selector ran. It also cannot find transition commands hidden in unrepresented compact OFC node bodies. Thus it strengthens the negative evidence for these decoded owners but does not change the safe boundary: current-world/slot state and `ENG_gf_SpecialTime` at cinematic entry require a complete execution trace or runtime snapshot.

## Retail global-AI startup resources

A read-only walk of the local `sally_clean.bf` start resource fills in an important gap in that EVE-only audit. The BIG header's `startKey` is `71003FF9`; its entry is `univers.oin`. The serialized AI instance begins with references to model `71003FF3` (`univers.omd`) and instance variables `71003FF8` (`univers.ova`), matching Iris's `AI_ul_CallbackLoadInstance` two-key reader (`external/irisEng/ai_common.c:1387-1406`). The model's serialized key/type list points to variable descriptor `71003FF2` (`univers.ova`) plus these OFCs: `71003FF1` (`univ_init.ofc`), `71004002` (`univ_go.ofc`), `710046D6` (`univ_exec_get_world_key.ofc`), `7100C854` (`univ_exec_new_game_init.ofc`), `7A000AF7` (`univ_exec_load_new_world.ofc`), `7100D95B` (`univ_exec_special_raz.ofc`), and `26003350` (`univ_volume_manager.ofc`). This matches the model reader, which dispatches `.ova` and `.ofc` references by their serialized type IDs (`ai_common.c:1325-1384`).

`univers.ova`'s five periodic callback slots have only slot 2 populated, with key `71003FF1` (`univ_init.ofc`); its event-callback count is zero. This layout follows `AI_ul_CallbackLoadVars` (`ai_common.c:1124-1135, 1280-1310`) and is independently consistent with IrisTool's `BFScriptingVariablesChunk.java:660-693`. The OFC node records are 8-byte `tAINode`s (`external/irisEng/ai.h:7-14`), and the serialized category/function IDs map through the registries in `ai_functions.c:28-30,169-175` and `ai_common.c:498-524,1459-1472`.

The concrete startup hand-off is visible in the root function body: `univ_init.ofc` has 1,389 primary nodes; node 1386 pushes function key `71004002`, and node 1387 calls `AITrackCurChangeNow`. Iris's implementation replaces the current track callback/jump node with the supplied function and returns the “repeat this track” result (`external/irisEng/ai/ai_aifunctions.c:252-280`; `ai_common.c:711-759`). `univ_go.ofc` is therefore the next static callback target. In that function, node 62 pushes `7A000AF7` and node 63 calls `AIExecute`; `univ_exec_load_new_world.ofc` loads `world_key`, invokes `WORLoadList`, and stores the returned slot index in `world_loaded_id`. `univ_go.ofc` also executes `univ_exec_get_world_key.ofc`, which contains `WORGetKey`, and has a `WORActive` call at node 80. The selector IDs are confirmed by Iris's registry (`ai_functions.c:169-175`), while world-list loading and activation are implemented in `ai_worldfunctions.c:24-117`.

The global-AI inspector now recognizes source-backed engine-call bindings when a serialized scalar-variable operand is adjacent to the call and the returned value is adjacent to an `Affect`. For the retail `univ_exec_load_new_world.ofc`, it reports `WORLoadList(world_key) -> world_loaded_id`. Iris's wrapper pops one integer key, calls the world-list loader, then pushes the returned index (`external/irisEng/ai/ai_worldfunctions.c:100-120`); Jaded declares the same one-INT-to-INT signature and its wrapper pushes the returned value (`external/jaded/src/libraries/AIinterp/Sources/Functions/AIdeffct.h:213`; `AIfunctions_wor.c:637-646`). `Affect` assigns that result to the serialized destination (`external/irisEng/ai/ai_keywords.c:1178-1207`). The UI/audit reports only the adjacent linear operand pattern; it does not reconstruct the runtime value in `world_key`, prove that the containing branch ran, or evaluate the assigned slot index. On the retail `sally_clean.bf`, `univ_init.ofc` (`71003FF1`) changes the current track to `univ_go.ofc` (`71004002`); from that function, node 63 links to `univ_exec_load_new_world.ofc`. With those source-backed names, `univ_go.ofc` has this more concrete static path:

- Node 0/1 executes `univ_volume_manager.ofc`; node 2 reads `load_world`, and node 3 exits at the function end when it is false.
- On the load path, nodes 4-6 clear `load_world`. Nodes 7-10 conditionally execute `univ_exec_new_game_init.ofc` when `i_force_newgame_reinit` is true.
- Nodes 23-26 compare `i_last_loaded_world_key` with `world_key`. A false comparison jumps to node 58, which copies `world_key` to `i_last_loaded_world_key`, validates save state, and executes `univ_exec_load_new_world.ofc` (nodes 61-63). That helper reads `world_key`, calls `WORLoadList`, and stores the returned universe slot in `world_loaded_id`.

These are control-flow edges and linked function/resource names, not inferred branch outcomes for a particular play session. `world_key`, the `WORLD_Key_Map_*` arrays, `load_world`, `i_force_newgame_reinit`, save data, and the universe slot table all require live values to determine which route ran. The parser does not execute the function or evaluate a branch from a serialized default.

In Iris, `WORLoadList(key)` sets the loading flag, calls `WOR_pst_Universe_AddWorldList`, and returns the resulting universe-table index (`external/irisEng/ai/ai_worldfunctions.c:100-120`). `WOR_pst_Universe_AddWorldList` reads ordered 8-byte key/value pairs from the WOL resource, merges each nonzero root key, then resolves/activates objects, rebuilds the EOT callback table and assigns `currentWorld` (`external/irisEng/world.c:2705-2873`). `WORActive(index)` separately marks that table entry active and sets `currentWorld` from the active-world lookup (`ai_worldfunctions.c:43-55`). Thus a WOL describes the roots used to assemble the loaded world; it is not the set of script owners dispatched by that world, and `WORLoadList`'s return value is a runtime slot index rather than another world key. Iris and Jaded both currently implement `WORLoaded` as an unconditional `1` (`irisEng/ai_worldfunctions.c:8-17`; `jaded/src/libraries/AIinterp/Sources/Functions/AIfunctions_wor.c:667-676`), so do not model that selector as an asynchronous readiness wait based on its name.

This explains why the archive-wide EVE-owner search found no `WORLoadList` or `WORActive` calls: the global universe AI model is a separate owner/resource chain and contains executable OFC bodies.

The `world_key` producer is now decoded from the retail archive's linked `univ_exec_get_world_key.ofc` (`710046D6`, 2,811 nodes) and cross-checked against Iris's compiled `map_manager` source (`external/irisEng/ai/ai_bge/ai_compiledscripts_global_mapmanager.c:558-1408`). `univ_go.ofc` calls it directly at node 22. The helper has two inverse lookup modes, selected by `i_get_map_id`. When set, it clears the flag, initializes `world_key` to `-1`, reads the current key with `WORGetKey`, scans the table by key, and writes the matching `world_ID`. When clear, it scans by `world_ID` and writes the corresponding `world_key`. This makes the table a script-owned world-ID/key translation, rather than a value inferred from a cinematic container's name.
