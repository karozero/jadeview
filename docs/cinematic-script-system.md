# Cinematic script graph

## How JadeView discovers a cinematic

A cinematic is assembled from a world record, not from a single `.i` event record. The PC archive reader follows the world dependency lists to GAO objects and their `q` brain records; each brain points to a script model and a model/instance OVA pair. World objects can also point to `Events` or `SceneEvents` records. Those keys are the bridge between an actor script and an event track. The event track itself carries time-stamped commands and animation data.

### Finding the analysis in JadeView

Open a BF, choose a row under **CUTSCENES**, then use the **CINEMATIC TIMELINE** panel. Scroll below playback, audio, camera and participants to **Script owners and event links**. Select an owner to inspect **Static trigger analysis**, callback slots, event tracks and the expanded **Saved flag / event links** section. The last section lists the selected owner's decoded flag accesses first; hover an entry for its source-backed explanation, then select a related owner to follow the link. These are static archive/source findings: they do not make a new effect visible in the viewport or prove that the game executes the callback.

The timeline now has a **Find script event owner, GAO, key, or command…** field near the top. It filters the lower **SceneEvents EVE inventory** by owner and event keys, channel index/target, decoded command name, or loaded command target; entering a query opens the matching inventory. For example, search a GAO key/name or `OBJRotateLocalY` to find channels that affect a prop without manually opening every list. The result count is the number of matching lists, not commands or confirmed runtime activations.

For callback-driven `TRA*` calls, expand **Inspect addressed EVE channels** directly below the resolved call to see its channels and recognized commands in context. When a command target belongs to the assembled cinematic world, select its row to frame the object. The separate **SceneEvents EVE inventory** remains available for browsing all event lists. This is a navigation and inspection improvement; it does not run the scene's script VM.

The `TRA*` call inspection also evaluates a narrow, source-confirmed case: a direct `AI_EvalFunc_OBJ_FlagsIdentityTest_C` against the current owner and a literal flag mask. It compares that condition (including `!` and `else`) with the owner's serialized GAO flags and reports whether that branch matches the saved flags. For example, the pump object's `0x0800F060` flags do not contain `0x02000000`. This is only a saved-state hint: earlier callbacks or gameplay may change flags before the call, so it does not prove that a branch cannot run at runtime. Other predicates remain unevaluated.

Direct `OBJ_CapaTest` checks on the current owner are described separately: Iris tests whether any bit in the requested mask is currently set. JadeView reports the mask and leaves the branch result unknown because live capabilities are runtime state, not an OVA snapshot. This applies to resolved and unresolved `TRA*` calls alike, so it can clarify a gate even when the call's event-list receiver cannot be joined to a serialized `SceneEvents` record.

Inside a decoded EVE channel, expand **Follow nested SceneEvents calls** to trace literal `TRA*` references into the target owner's `SceneEvents` channels recursively. It includes all-channel commands, resolves within the current world first, stops repeated channels as cycles, and marks missing/ambiguous links unresolved. The traversal is bounded and static; it does not execute commands or follow conditional runtime dispatch. An archive scan of all 91 FF containers decoded 18 channels containing nested calls: 149 resolved route edges and 6 cycle stops, with no unresolved route in those roots.

The channel inspector also has a collapsed **Raw EVE key payloads** view. It shows serialized value/tag pairs for format investigation; category, metadata, and type numbers remain raw unless a source-backed decoder recognizes them. In the elevator route `35009EF6` -> `1_1_obj_verin_axe.gao` `SceneEvents A9001DF1`, channel 0 has 25 keys over 8.5 seconds, 19 word-pair payloads, 6 keys with no decoded payload, and 19 decoded commands: 14 `OBJRotateLocalY` increments plus five `TRAPlay` calls. It has no decoded translation, rotation, or scale samples; the rotation is issued through script commands. Four child channels (2–5) each issue `OBJ_OrientTo` at their start; Iris/Jaded rotate the current object toward the referenced object while preserving its position. Channel 1 starts at 8.5 seconds and contains one float-typed `OBJRotateLocalY` call with value 12.0 radians over its one-second EVE event. Iris scales that angle by each event-frame time slice, and the local-axis math consumes radians. This identifies a procedural shaft spin sequence, though JadeView does not yet simulate nested EVE timing or apply it to the shaft preview. The nested chain is still a serialized route; runtime dispatch and whether the game started it remain unknown.

The same controller, `CINE_MACHINE_DEMARRE_EVENTS.gao`, has a source-reachable `TRAPlayAll` operation in `Cine_Events_Cine_exec_GoToEvents`, targeting its 32-channel `SceneEvents 35009EF6` list. The indexed callback path passes through `Cine_Events_cine_tests_depart` and includes an `OBJ_CapaTest(0x100)` alternative; the live capability and whether the callback ran are unknown. This links the script callback to the EVE roots without assuming all channels were active. The graph report is `artifacts/cinematic-elevator-float-v57/FF006B96-35009EF6-script-graph.json`.

For `OBJ_OrientTo`, `OBJ_HierarchySet`, `OBJ_Rejoin` and `OBJ_RejoinAndOrient`, JadeView marks the first literal object argument and lets the user select/frame that object when it is loaded in the cinematic world. These argument types come from the engine function signatures; other numeric arguments are not guessed to be object keys.

Float-literal EVE arguments (serialized value type `0x22`) now pass through the same literal-call decoder as integer and object literals, retaining their original 32-bit value for source-aware function interpretation. The elevator spin command was previously omitted because the decoder rejected that argument type; the regression fixture verifies the selector, raw float bits and 12-radian description. Multi-scene graph audits after the change completed for `FF005833 / BF00218E` (31 owners, 131 calls), `FF0045A2 / 3500B8EA` (83 owners, 544 calls) and `FF00791B / BF003BD1` (14 owners, 11 calls). The first and third had no decoded axis-rotation commands; the second had two, with values `-0.02` and `0` radians. The reports are under `artifacts/float-call-audits-v56/`. This checks the new typed-argument path beyond the elevator while keeping unknown functions and arguments uninterpreted.

JadeView now builds that graph from the currently loaded archive data. The cinematic inspector lists script owners in the selected cinematic world, puts owners whose `Events` or `SceneEvents` key matches the selected clip first, shows model callback names, decodes serialized model/instance OVA values, and decodes object-reference OVA fields in both directions. It also includes script owners from another loaded world when their GAO key is referenced by the selected cinematic's serialized OVA links, animation/transform tracks, actor rigs, or typed-message context/`Gao`/`Gao2` fields. For those linked owners it follows additional serialized OVA references and the targets/recipients of their own linked event records; unrelated owners outside that reachable graph stay out of the list. The incoming-links view identifies the source OVA field or event command/message that reaches the selected owner. This exposes reusable actor brains and their serialized event-track links alongside cinematic controllers. For a linked actor owner, the inspector also lists the parsed skeleton action-table slots with source clip and shape keys; it does not mark an action as active unless a cinematic body-action timeline selects it. The label shows the source world, and the UI explicitly treats the relationship as a serialized link rather than proof that the brain ran. Selecting a resolved object reference frames that object in the viewport; selecting an incoming owner opens its script details. **Decoded track commands** lists commands the current decoder recognizes, names them through the engine selector catalog, and seeks to the command time when selected. OVA values are saved snapshots: they do not show live special flags, capability changes, or VM execution state. A separate OVA-use view joins source-indexed reads/writes through local pointers resolved to `instanceVarDataCurrent` or `instanceVarDataModel` to configured callback paths, then matches those names to the owner's serialized OVA fields. It retains source line, alias, and enclosing `if` conditions. Address-taking, unresolved pointer aliases, macros, and callback execution remain limits; reaching a field in source does not prove the callback ran.

The incoming-links list also includes direct references from the selected cinematic clip itself. Literal engine calls link their command target; typed messages keep the EVE execution object separate from `Gao` and `Gao2`. Selecting one of these clip links pauses and seeks to its source timestamp. In `FF005833 / BF00218E`, this exposes `Cine_ecran_explik_invent.gao` receiving `OBJ_CapaSet` at 44.783 s, and the two `Cine_SFX_*ventilo` owners receiving capability changes at 42.733–43.533 s. These links identify serialized commands and times; they do not prove the target's prior state or that a runtime callback/trigger ran. The graph-audit JSON writes the same edges as `SelectedClipIncomingLinks` for cross-checking.

Decoded EVE commands also describe source-confirmed world-scheduler operations. `WORPause` / `WORUnPause` target a universe world-table slot and a GAO identity-flag mask: Iris sets or clears runtime pause bit `flags2 0x04000000`, updates active state on unpause when gate `0x00400000` allows it, and requests the table/visibility rebuild. `WORPlayAbsTime` sets global `ENG_gf_SpecialTime` and `ENG_gf_SpecialDT`; the engine reinitializes loaded worlds and advances them in special-time steps before clearing the values. JadeView shows the literal serialized arguments and event time, but does not map a runtime world-table slot to an archive world key, decode unknown float literals, or simulate the resulting world state. These descriptions use Iris implementations in `ai_worldfunctions.c` and `engine.c`, not scene-specific rules.

The callback inspector reads the model's referenced OVA record and preserves its five serialized callback positions, including empty slots. Callback keys are named through the Iris compiled-function table. Script-model function references are shown separately when available; they are not substituted for missing or malformed owner callback-slot data. Iris `AI_ul_CallbackLoadVars` confirms the fixed five-key layout after the variable-default block, while `AI_ReinitInstance` copies those slots into the per-owner instance. The engine command catalog maps event-command selector bytecode to Iris engine function names. Neither catalog executes callbacks: configured positions and linked track commands do not establish which callback was scheduled or ran in a game session.

The selected owner also shows a **World AI callback scheduling** summary derived from serialized GAO header words. Iris reads the word following the GAO identity flags as initial state flags and applies mask `0x7B9C0080` to initialize runtime `flags2`; serialized bit `0x40000000` is separately mapped to runtime bit `0x00400000`. A raw serialized `0x00400000` bit is discarded by the initial mask and does not itself block activation. `WOR_ActivateObjectIfFlagsAllow` rejects ordinary activation while runtime flags2 intersects `0x04400000` or `0x10`; when `ENG_gf_SpecialTime` is nonzero it follows a separate `0x04000000` path. Iris's `EOT_SetOfEOT_Build` places activated objects whose identity flags include `0x20` in `AICallbacksTablePF`; `AI_MainCall` then checks processed state, distance/extra flags and object state before `AI_RunInstance`. The inspector reports the serialized words and the source-mapped `0x00400000` gate, but it does not claim runtime table membership or callback execution because other flags and `ENG_gf_SpecialTime` are runtime state. This links a brain-bearing GAO to the engine scheduler without treating every configured brain as an always-running script.

The pre-release Jaded source was cross-checked separately and is not used as a drop-in substitute for retail scheduling semantics. Jaded's `OBJ_C_IdentityFlag_AI` is also `0x20`, and `EOT_SetOfEOT_Build` copies AI-flagged active objects into `st_AI`, but its `WOR_ActivateObjectIfFlagsAllow` uses sectorization plus `ForceInactive`/`InPause` control flags; its `AI_MainCall` gates execution with `ForceInactive` and `SectoInactive`. Retail Iris instead exposes `flags2` activation masks, `ENG_gf_SpecialTime`, and the processed/distance/extra-flag checks. These matching table roles and differing runtime gates are documented in `external/jaded/src/libraries/ENGine/Sources/OBJects/OBJconst.h`, `EOT/EOTmain.c`, `WORld/WORmain.c`, `AIinterp/Sources/AIengine.c`, and the corresponding `external/irisEng/world.c` / `ai_common.c`. JadeView therefore labels its current summary as retail-Iris-derived; the 2002 source is supporting historical context only.

The collapsed **Source calls using linked objects** section joins each source-reachable engine call to object fields in the selected owner's serialized OVA when the call's source arguments or aliases identify that field. It reports the resolved target, API arguments, callback path, source line, and known branch conditions without interpreting the call as executed. In the hangar `BF00218E` archive audit, this exposes `PNJ_Drone_Mdisk_R.gao`'s instance field `des_o_drone_vert → PNJ_Drone_Mdisk_V.gao`: when that reference is non-null, the init callback aligns/parents the component and issues inactive/invisible changes; a reachable plug-mode callback issues the corresponding visible/active changes only under its recorded `i_flag_mdisk_pris` branch. The existence of those commands does not prove that the owner callback ran or that its source branches passed, but it makes the scripted component relationship inspectable without adding a rule for that actor or scene. The same generic view exposes `Cine_ecran_explik_invent.gao` calls to its serialized computer-switch and radio references from `mpegplayer_init`/`mpegplayer_loop`, including source guards around capability and sound changes. In the `SceneEvents EVE inventory`, literal command rows whose targets are present in the active cinematic world are clickable and select/frame that object, making it easier to inspect the fan parts, monitor and drones without searching the Outliner by key.

The bundled source-call index contains 53 `OBJ_FlagsIdentitySet` sites with literal set/clear masks; none changes identity flag `0x20`, the AI callback-table membership flag. The three cross-checked clips (`FF005833 / BF00218E`, `FF0045A2 / 3500B8EA`, and `FF00791B / BF003BD1`) likewise contain no reachable callback that changes this bit. The hangar's `PNJ_Drone_Mdisk_R.gao` does have a source-resolved init call that sets mask `0x18000`, but this does not alter AI-table membership. This rules out one tempting explanation for actors that stay in T-pose: there is no indexed script call changing their `0x20` scheduler flag. It does not rule out runtime activation gates, brain initialization state, world transitions, or command/message paths outside the indexed callback graph. Iris's behavior for such a change is known: `OBJ_FlagsIdentitySet_C` applies `(setMask | (~clearMask & currentFlags))`; clearing an already-set `0x20` frees the AI instance and removes the object from `AICallbacksTablePF` (`gameobject.c`, around lines 2276–2281), while setting it follows the detection-list allocation path (`gameobject.c`, around lines 2256–2260). These are engine semantics, not evidence that any particular scene executes such a transition.

The selected clip audits report flag `0x20` on all brain-bearing script owners: 31/31 in `FF005833 / BF00218E`, 83/83 in `FF0045A2 / 3500B8EA`, and 14/14 in `FF00791B / BF003BD1`. This is a serialization/scheduler consistency check within owners already identified by the brain pointer; it does not cover non-brain world objects or validate runtime activation.

The second GAO header word also carries state relevant to that scheduler mapping. In those same clips, 11/31, 62/83 and 5/14 brain-bearing owners respectively have serialized bits that map to runtime `flags2 0x00400000`, which blocks ordinary activation when `ENG_gf_SpecialTime == 0`. Examples include `Cine_Ecrou_01.gao` (`606000AC`) in `BF00218E`, `Cine_SFX_Soleil.gao` (`6060002C`) in `3500B8EA`, and `Cine_Lum_SAS_D.gao` (`60600024`) in `BF003BD1`. This narrows the static explanation for why some configured script owners are not normally scheduled, but special-time mode and later runtime flag changes can alter eligibility; the stored word alone does not reveal whether a callback ran.

The inspector also uses a generated source call graph to follow direct Iris `AIExecute`, `AITrackChange`, `AITrackCurChange`, `AITrackCurChangeNow`, `AICBAdd`, and `AICBDel` calls from the owner's configured callback slots. It preserves literal track indices on `AITrackChange` edges and distinguishes `AITrackCurChange` (sets the current callback track) from `AITrackCurChangeNow` (replaces it immediately). This recovers chains such as `mpegplayer_init → mpegplayer_loop`, which were previously missing because the ordinary current-track change was not indexed. It also records `AICBAdd`/`AICBDel` function references and literal callback IDs; only registration edges are traversed as possible asynchronous callback routes, while deletion edges remain visible in the source graph but do not claim the removed function is invoked. Iris `AICBAdd` stores a callback function and ID on an AI instance, and `AI_ExecCallback` later invokes matching registrations when the engine dispatches that ID. JadeView retains the numeric ID rather than guessing which gameplay event will dispatch it. For registered IDs, the inspector now joins literal `AI_ExecCallback` / `AI_ExecCallbackAll` call sites from the bundled engine source. For example, the source shows callback ID 2 dispatched through the world callback table in `engine.c`, ID 3 from animation/world processing, and IDs 0/1 in geometry rendering paths. The inspector lists exact source file, line, and call expression rather than asserting broader gameplay meaning. The generated list comes from `tools/Generate-CinematicCallbackDispatchCatalog.ps1` and is embedded as `script-callback-dispatch.json`. The owner-field access catalog is generated from bundled Iris source with `tools/Generate-CinematicScriptOvaFieldAccessIndex.ps1 -SourcePath external/irisEng/ai -FunctionNamesPath src/Features/Cinematics/Data/script-function-names.json -OutputPath src/Features/Cinematics/Data/script-ova-field-accesses.json.gz`; the application uses the embedded catalog at runtime.

This join was exercised on three actual clips from the installed archive: in `FF005833 / BF00218E`, `_PJ_Sally.gao` has a route registered for ID 3, whose source dispatch sites are in `animation.c` / `world.c`; in `FF0045A2 / 3500B8EA`, effect owners expose ID 0 render dispatch sites in `graphicsobjects/geo.c`; in `FF00791B / BF003BD1`, `_PJ_Militaire.gao` exposes ID 2 at `engine.c`. This shows the same source join resolving across separate cinematic families without actor-name rules. It still does not prove that any given owner entered the engine callback table or passed its runtime eligibility checks.

A collapsed **Source callback and trigger paths** list shows each model-referenced nested function and one shortest source path from a configured owner slot, followed by engine call sites for any registered numeric IDs. Dispatch edges are annotated with matching Iris call-site file/line and enclosing source `if`/`else` expressions when the source index can bind the exact function reference; the path is still a static candidate, not a runtime route. Message descriptions use the same path resolver. Cinematic script graph audit JSON exports the nested paths for local owners and actor participants. Traversal is limited to functions referenced by that script model, so a name elsewhere in the source tree does not make the owner appear to support it. Nested paths and engine call sites do not prove that a world contained the owner in the callback table, that branch conditions or process gates passed, that a changed track ran, or that a callback executed in the game. The call-site index is evidence about dispatch locations, not a reconstruction of live runtime state.

The expanded **Iris source evidence** panel lists literal message IDs read from the selected owner's queue, with callback paths and source lines. The index covers both `MSGGetByID_C` calls with a literal ID and `MSGGet_C_CURRENT` results whose copied message structure is later compared against a literal `msgID`. Cinematic and world graph audit JSON includes these `SourceMessageReaders` rows. For typed cinematic messages without a recognized field-level explanation, the timeline falls back to these source-indexed reads in the resolved EVE execution owner's reachable callback graph. It links a literal message ID to the receiving callback path and source line, while explicitly leaving payload interpretation unresolved.

Source `MSGSend_C` routes are joined to those readers only when exactly one unbranched source assignment gives the message buffer's literal ID, the destination is the current owner or resolves through one unique source object/OVA reference, a unique script owner exists for that target, and one of its reachable callbacks reads the same ID. The inspector exposes matching routes and can navigate to the receiver owner; graph audits export them as `SourceMessageRoutes`. This remains a possible static route: message queues hold at most five records in Iris, so overflow and execution order may prevent delivery, and JadeView does not claim that the callback ran. Dynamic IDs, conditional or multiple ID writes, indirect aliases it cannot uniquely bind, branches not evaluated, and targets without a resolved script owner remain unlinked. The generated generic reader index is reproducible with `tools/Generate-CinematicScriptMessageReaderIndex.ps1` against the bundled `external/irisEng` source and `script-function-names.json` catalog.

Production audits of `FF005833/BF00218E`, `FF0045A2/3500B8EA`, and `FF00791B/BF003BD1` now export 4, 7, and 4 source send-to-reader routes, respectively, alongside reachable queue readers on cross-world actor owners. A world audit of `FF005520 / 01_05_entrepot_enlevement_peyj` (103 script owners) independently found 12 literal type-30 routes to `TXT_Sally.gao` (`7200064E`), including reusable `ES-54_*` and grille action-reaction owners. The receiver model's `Cine_Textes_CiTxt_reception_messages` callback obtains the current object's queue via `MSGGet_C_CURRENT`, then checks `msgID == 30`; Iris's `MSGSend_C` copies the complete message to the destination queue, capped at five entries. This proves a static possible route and source-level receiver behavior, not that a particular owner was instantiated, the send branch passed, the queue accepted the message, or the callback ran. The three cinematic samples contain no new generic typed-message explanations; route evidence is visible under the selected sender's **Iris source evidence** panel.

The source graph also resolves a subset of indirect callback dispatches through function-pointer fields. When an Iris function assigns a known script function to `object->field`, and another function dispatches that same field as a `tAIFunction*`, JadeView records a candidate edge with the field name and assignment function/file/line. The owner model's function list still constrains which candidate is displayed, and exact symbol matching is used when attaching source call sites so similarly prefixed function names do not get conflated. This is source-level data flow within one source file; it does not resolve arbitrary aliases, runtime field mutations, cross-file pointer assignments, or prove that the field held that function when the game ran.

### Archive-wide body-action coverage and gameplay handoff

The `--archive-cinematic-body-coverage` audit scans all 91 cinematic containers in the current BF archive. In this archive it found 1,232 clips and 439 skeletal actor/clip bindings: 296 have decoded body-action segments and 143 do not. The no-action cases split into 114 root-transform-only, 26 direct-bone-track-only, and 5 unresolved-action-request bindings. This measures decoder coverage and highlights where the cinematic stream lacks a pose source; it does not classify every case as an error.

The script-graph audit now uses the assembled cinematic world and includes object targets from serialized transform tracks when finding linked brains. For `FF00791B / BF003BD1`, it resolves Peyj to `_basic_peyj`, brain `9E001C77`, model `35001FF8`, callback `companion_co_init`, and base `Events=35009544`. The base event record lasts 2.367 seconds but contains no decoded calls. The companion brain's source-reachable callbacks contain many possible action requests; their selection depends on runtime mode and branch inputs absent from the cinematic BF snapshot. JadeView therefore exposes the brain and event link but cannot identify Peyj's active action at handoff, so the preview keeps the existing unresolved-state diagnostic instead of choosing a guessed idle.

The same inspector now also lists source-confirmed `WORPause`, `WORUnPause`, and `WORPlayAbsTime` calls found inside those reachable callback functions, with the function name, original argument expressions, and source file/line. For example, Iris source calls `WORPause(v5, 0x20)`: the inspector preserves the literal mask and reports that `v5` is assigned by `AI_EvalFunc_WORCurIndexGet_C`, while leaving its live world-table slot unevaluated. This makes world activation and special-time operations visible even when they are not serialized as direct EVE timeline commands. The index is generated from Iris script C sources and filtered through the selected owner's configured callback slots and model function list. It does not evaluate branch conditions or prove that the operation ran at runtime. For callback-driven `TRAPlay*` calls, the inspector resolves each EVE channel target to a loaded object name where unambiguous; selecting a target present in the assembled cinematic world frames it in the viewport.

Reachable source-call evidence now retains both sides of unbraced `if/else` statements, including a call that begins at the first character of an `else` body. This matters for source callbacks that encode a flag choice across complementary branches; for example, `Detect_o_Capa_doc_une_a_vrai` now preserves its `else` branch for the `ARRGlobalIntFlagSet` call at `ai_compiledscripts_detectors.c:2415`. For direct `ARRGlobalIntFlagTest` comparisons against an effective OVA integer of 0 or 1, the inspector also reports the configured required state (set/clear). Flag links compare that state with known event-track set/clear commands and label a matching or opposing configured value; timing, alternate branches, compound gates, and live save state remain unevaluated. A regression check covers both branch provenance and the configured polarity/link relation.

The flag-link comparison was verified in the installed archive on `FF005833 / BF00218E`: the `CINE_APRES_MDISK_EVT02.gao` track's literal set of flag 2166 at 44.783 s links to two configured readers whose associated-flag predicate requires that flag set. The audit labels the configured values as matching and retains the explicit unknown-runtime-order limit; it does not infer that either reader executes after the event command.

The same section now groups direct `AI_EvalFunc_*` calls from every source function reachable through the configured callback slots. The generated catalog contains 42,578 direct call sites across 1,405 named source functions and is embedded compressed; the UI shows API counts plus representative raw argument expressions, function names, and source locations. The index also records enclosing `if` expressions for braced blocks and simple unbraced statements, preserving the source text as conditions rather than evaluating them. Paired `else` branches are linked to their originating `if` as an `else of if (...)` source relation, without evaluating negation. Nested `else if` chains now retain each enclosing source relation: a call in an alternative branch can show both the rejected outer `if` and the selected inner `if`; a final `else` can show rejected conditions for each preceding branch. This syntax scan handles recognizable `if`/`else`, braced bodies, and simple semicolon-terminated statements. It does not parse or evaluate loops, switches, macros, indirect control flow, or runtime predicate values, and it is not a general C parser. Argument parsing respects nested calls, casts, brackets, and quoted strings; it preserves expressions such as `a1, v3, 9` without evaluating them. For local variables used as call arguments, the inspector shows a bounded source assignment chain: the latest lexical assignment visible before the call plus assignments to local identifiers referenced by that expression. The chain is limited to three levels and 24 entries per call. In `Cine_Events_cine_play_eventtrack`, this traces `v5` through `AI_MainActor[...]` and back to `v8 = *AI_MainActor`; it is source provenance, not a resolved actor identity, because branch conditions and the selected main-actor slot are runtime-dependent. The graph audit retains these assignments in `SourceEngineCallSummary[].Examples[].ArgumentAssignments`, with `Depth` indicating the chain level. The inspector also matches source member fields used directly in a call or found anywhere in the bounded local assignment chain to the owner's effective OVA field. For example, `Cine_ecran_explik_invent.gao` passes `v5` to `OBJ_CapaTest`; Iris assigns that local from `des_o_Interrupteur`, whose instance OVA resolves to `OBJ_Interrupteur_ordinateur.gao`. A matched field in a conditional assignment is shown as a candidate source path; branch conditions may select another pointer or null, and actual execution is not evaluated. Graph audits export source-object and OVA-field joins as `SourceObjectArgumentBindings` and `SourceOvaArgumentBindings`. For source `MSGSend` calls, the same index records the latest lexical assignments to the passed `tMessage` buffer fields (for example `msgID`, `Int1`, `Gao`, and `Gao2`), with source lines. A buffer can retain values assigned earlier, and mutually exclusive branch assignments are not evaluated, so these are source candidates rather than proof of the exact delivered payload. It was exercised on `BF00218E`, `3500B8EA`, and `BF003BD1`; for example, the decryptage report exposes `Cine_init_cableventilo_fixe.gao` calls to `OBJ_CustomBitsSet`, `COLBVObjectObject`, and `AIExecute`, and the monitor owner calls to `OBJ_CapaSet` and material APIs. This inventory is evidence of direct source calls, not a decoded EVE event, argument evaluation, branch result, or execution trace; helper calls outside `AI_EvalFunc_*` and indirect calls are not included.

The generated index is compressed and generic across the bundled Iris script sources.

The message inspector now decodes type 49 only for script owners whose assigned callback graph reaches Iris's `companion_co_exec_get_message` handler. Iris uses this message to update a companion's requested status, optional action, placement, facing direction, and world in the shared companion table, then selects a companion mode. `Int1=3` also writes the collision-start matrix from `Vector1`; `Int1=4` defers `Int2` as an action instead of immediately calling `ACTActionSet`. Zero vectors and `Float2=0` select the receiver's current position, sight, and world. The source also skips unchanged status/world updates (except status 3) and defers application in modes 9 and 17.

This is deliberately callback-scoped: Iris also assigns other meanings to type 49 for unrelated script families (including Crochax scale, aircraft mode, and SFX lighting), so JadeView must not label every numeric type-49 message as a companion command. In the UI, inspect the typed messages under **Cinematic Timeline** or expand a serialized **SceneEvents** channel; the explanation includes the resolved EVE execution owner and callback path. The values are static message data and source behavior, not proof the callback ran, a runtime branch passed, or an actor appeared in-game. Regression checks cover immediate status/action/placement and the deferred status-4 action, plus rejection of an unrelated callback owner.

### World activation versus AI callback execution

The selected owner's **World AI callback scheduling** evidence now reports the two engine gates separately. A serialized status bit `0x40000000` maps to runtime `flags2 0x00400000`; Iris rejects ordinary-time activation when `flags2 & 0x04400000` is nonzero, so this serialized bit is a confirmed ordinary-activation blocker at load unless runtime state changes. During nonzero `ENG_gf_SpecialTime`, the alternate activation path instead requires `flags2 0x04000000`, and JadeView reports whether the serialized initial word contains that bit. After activation, `AI_MainCall` skips invalid or already-processed entries, optionally requires distance when `extended->extraFlag & 0x4` is set, redirects processing through unprocessed hierarchy parents, requires an allocated `AIInstance`, and skips `AI_RunInstance` while runtime `flags2 0x00400000` remains set.

These are ordered source-derived eligibility checks, not a claim that a callback ran: the BF snapshot cannot show later flag mutations, special-time state, table membership, distance, hierarchy changes, instance allocation, or callback results. The mapping is from retail Iris `gameobject.c` (GAO state load and `OBJ_UpdateStatusFlagRTL`), `world.c` (`WOR_ActivateObjectIfFlagsAllow` and EOT construction), and `ai_common.c` (`AI_MainCall`).

Saved-flag identifiers resolved through callback-local variables are now causal with respect to the indexed source call: only a unique assignment at or before that call line may supply the flag number. Later assignments are ignored, and a non-unique assignment stays unresolved. This prevents a later write in the function from being mistaken for the value used by an earlier trigger/test; it does not attempt general C data-flow or path-sensitive alias analysis.

`Detect_o_Zone` starts its timer for any `des_f_minuterie != 0`, not only positive values. Its follow-up calls `TIMEElapsed(start, duration)`, whose Iris implementation is `currentTime - start >= duration`; therefore a negative configured duration is already elapsed once its nonzero start timestamp is recorded. The inspector reports that source behavior instead of treating a finite negative duration as a missing timer. It still does not simulate collision edges, current time, or flag mutations.
