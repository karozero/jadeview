# Cinematic script graph

## How JadeView discovers a cinematic

A cinematic is assembled from a world record, not from a single `.i` event record. The PC archive reader follows the world dependency lists to GAO objects and their `q` brain records; each brain points to a script model and a model/instance OVA pair. World objects can also point to `Events` or `SceneEvents` records. Those keys are the bridge between an actor script and an event track. The event track itself carries time-stamped commands and animation data.

For EVE AI-function key wait/retry flags and their Iris source behavior, see [EVE AI-function events](game-script-eve-function-events.md).
For a cross-subsystem index into the Jaded sources and guidance on separating its later-engine behavior from retail PC, see [Jaded source map](jaded-source-map.md).

### EVE-to-animation action handoff

An EVE AI-function may call `ACTActionSet` inline during the world's EVE pass.
Iris does not switch the rendered action immediately: when EVE is active,
`ACT_SetAction` stores a pending action and the elapsed intra-frame time
(`external/irisEng/actions.c:212-218`). The following `ANI_MainCall` processes
the previous action to that time, consumes the pending action, then advances
the new action through the remainder of the same engine call
(`animation.c:1381-1383,1424-1457`). Jaded corroborates this schedule through
its `ACT_SetAction` queue and `ANI_PlayLeadAnimation` handoff
(`external/jaded/src/libraries/ENGine/Sources/ACTions/ACTcompute.c:671-686`;
`ANImation/ANIplay.c:1071-1144`). The same high-level order is present in
retail Iris `ENG_OneWorldEngineCall` (`engine.c:180-215`).

JadeView places a resolved, time-addressed action request at its source event
timestamp and samples the resulting action continuously from that point. This
preserves the old-action/new-action boundary in timeline space, but cannot
reconstruct the native frame cadence or exact intra-frame render boundary.
For callback-generated actions, the callback's live eligibility and state gates
remain separate from this handoff rule; see
[owner start lifecycle](cinematic-owner-start-lifecycle.md).

### Owner-wide EVE loop reset

Retail Iris PC treats an auto-looping EVE channel with `boneID == 255` as a list-level restart: `EVE_RunningTracksAtStart` resets the event cursor and completion bit for every currently running channel owned by that EVE list. It does not restart stopped channels, and it preserves the running and pause state, so a paused-but-running channel has its cursor reset and remains paused. The runtime running bit is distinct from the serialized `RunningInit` flag: `TRAPlay` can start a non-`RunningInit` channel, which is then included in the list-level reset. This is visible in Iris `events.c` (`EVE_RunningTracksAtStart`, the `boneID == 255` loop branches, and `EVE_ReinitTrack`); Jaded's later engine source has the same branch. JadeView carries those sentinel-loop boundaries into peer channel clocks so transform, event-call, and message sampling restart together in preview and synchronized export. This is timeline reconstruction from serialized EVE data; it still does not simulate whether the owner entered the live world's EVE dispatch table. Regression checks cover repeated peer resets, `TRAPlay`-started peers, stopped peers, and pause preservation. A static sweep parsed all 91 scene containers in the current `sally_clean.bf` and found zero `boneID == 255` auto-loop roots, so this source-confirmed rule is not yet exercised by a scene from that archive.

The assembled preview now follows effective object references from script owners linked to the selected clip, then follows uniquely resolved script owners on referenced GAOs. Instance OVA references override model references with the same field name; ambiguous owners are left unresolved. Targets from nested `SceneEvents` commands and transforms are included as well. This makes script-linked actors and props available to the preview without inferring their activation from names. It does not evaluate callback branches or make every included target visible. On `FF001FBE / 35009F74`, the `CINE_PIEGE_PORTE_LOBO_EVENTS.gao` owner links to the clip and references `_PJ_Militaire.gao` (`7100596B`). Its two source `ACTActionFrameSet` requests for action 201 remain unresolved against Militaire's base action table. A separate same-world owner, `CINE_INIT_MILI_EVENTS.gao` (`35009652`), exposes a plausible dynamic path: its `SceneEvents=35009655` channel 2 merges slots 200–230 from `CINE_01_04_ACK_Mili.gao` (`3500965A`), then sends companion message 49 with status 3 and action 201 to Militaire. The source kit contains slot 201 as action resource `35009636`, and Iris's companion handler passes that requested action to `ACTActionSet`. This event owner has an immediate `Cine_Events` lifecycle, but its serialized start tests include actor activity and saved special flag 2007 (`mask 0x104`); the archive cannot establish that those runtime gates passed. This is a candidate explanation for the missing pose, not evidence that the event ran. The **EVE & actions** tab now exposes independently gated script-owned `SceneEvents` with gate state/uncertainty and explicit per-owner preview. This may help inspect the candidate action path, but it does not establish that the owner ran in the game and does not apply the action globally.

### Scene archive `.ofc` body coverage

The archive-wide cinematic script index now records whether model-linked `.ofc` resources contain full serialized function bodies or only the compact metadata layout. In the current `sally_clean.bf` audit, 5,876 model-to-function references were matched against the Iris function-key catalog; 4,711 resolved to scoped `.ofc` resources and 1,165 did not. The 4,711 resolved references reduce to 607 unique payloads, and every payload parses as compact metadata with its declared node-byte count and local constants but no node body; none contains a full body and none is an unrecognized payload. The audit therefore cannot decode scene-owner bytecode or extract its literal `AITrackChange` calls from these resources. The indexed Iris C callback source and serialized OVA/EVE data remain the available evidence for those owners; neither proves a branch ran. The global startup audit is a separate resource path and can expose full serialized bodies where they are present. These counts are archive-specific and are written to `artifacts/export-verification/archive-cinematic-script-index.json` by `--archive-cinematic-script-index`.

A structural scan of the generated script-graph reports found 14 separate EVE channels across four containers (`FF001FBE`, `FF0045A2`, `FF005833`, `FF00791B`) that contain both an `ACTKitMerge`/`ACTKitMergeOver` call and a type-49 companion message. Examples include `CINE_INIT_MILI_EVENTS` in `FF001FBE / 35009655`, `CINE_OUVRE_SAS_EVENTS` in `FF00791B / 20007991`, and `CINE_APRES_MDISK_EVT02` in `FF005833 / BF00218E`. The repeated order is significant: the track can extend an actor's runtime action kit before the companion callback requests a slot. These channels belong to separate script-owner EVE lists, often alongside an independent cinematic clip. `Cine_Events_cine_firstinit → cine_init → cine_tests_depart → Cine_exec_InitialiseCine → Cine_exec_GoToEvents` controls whether the owner calls `TRAPlayAll`; serialized gates may depend on actor capabilities and saved flags. JadeView exposes independently gated owner lists in **EVE & actions** with explicit per-owner preview controls and candidate starts from unambiguous serialized flag writes or matching queued-message records. A selected owner can be overlaid at its preview start and included in synchronized export. This is not automatic VM execution: other gates and live state remain unknown, so manual inclusion can show content that the game might not activate.

When an explicitly scheduled cinematic, nested EVE channel, or manually previewed script-owner EVE list contains `MSGSendAll` type 49, playback now checks the addressed object's resolved script callback graph for `companion_co_exec_get_message`. For callback-confirmed companion receivers, non-deferred statuses convert a valid `Int2` into a body-action request at that event time. Status 4 remains deferred, `Int2=-1` means keep the current action, and unrelated or ambiguous receivers are ignored. These generated requests share the ordered event stream with same-time `ACTKitMerge` calls, so the source kit is installed before its action slot is resolved. This models only the body-action consequence of the serialized message; position/sight/world/status-table changes and companion mode selection remain outside this body timeline. Independent owner lists can be included through explicit preview controls, but JadeView does not execute their lifecycle predicates or live activation logic.

Iris's `ACT_ul_ActionKitCallback` reads ordinary action-kit entries as 8-byte records (action key plus a second field); its separate `/BIN` speed-mode path reads 4-byte keys. JadeView tests both layouts against the loaded archive's resolvable action resources and uses the layout with stronger resource matches, preferring the ordinary layout on ties. For Military's kit in this scene (`7100596B`, table `6C006831`, 928 bytes), the 4-byte interpretation resolves 100 action resources at sparse slots through 146. Neither interpretation supplies slot 201, so the missing request is not caused by decoding the table's second fields as extra slots. This confirms the archive boundary only; an action installed dynamically by an unobserved runtime path remains possible.

### Finding the analysis in JadeView

Open a BF, choose a row under **CUTSCENES**, then use the **CINEMATIC TIMELINE** panel. Scroll below playback, audio, camera and participants to **Script owners and event links**. Select an owner to inspect **Static trigger analysis**, callback slots, event tracks and the expanded **Saved flag / event links** section. The last section lists the selected owner's decoded flag accesses first; hover an entry for its source-backed explanation, then select a related owner to follow the link. These are static archive/source findings: they do not make a new effect visible in the viewport or prove that the game executes the callback.

For a selected object in the ordinary **ASSET INSPECTOR**, the **Script** tab appears when JadeView resolves that GAO to one archive script owner. It shows the owner's source world, brain/model and event links, AI track callback slots, optional engine-event hooks, and source-reachable state-effect candidates. Use it to inspect an object's script without first selecting a cutscene. Unresolved or ambiguous owner keys do not get guessed. Hook assignments and source calls are evidence of possible behavior, not proof of runtime dispatch; this tab does not execute callbacks or apply their effects.

Each callback state-effect candidate now also reports recognized current-owner identity-flag tests against the serialized GAO flags. These findings evaluate individual source predicates only; they do not combine nested conditions into a final branch result, and they do not model flag changes before the callback runs. Unknown predicates, callback scheduling and the effect itself remain unresolved.

For engine-event hooks with an Iris source call site, the tab also lists the direct `AI_ExecCallback` / `AI_ExecCallbackAll` call and source location. These links distinguish assigned event slots from events Iris actually dispatches in the recovered engine source. They do not encode every surrounding branch or the AI-instance eligibility checks, so they remain possible entry points rather than a runtime trace. Jaded-only event labels are shown without inventing an Iris call site.

The same source-evidence panel exposes **Dynamic AI callback registration candidates** for reachable `AICBAdd` and `AICBDel` calls. Each row preserves the callback source/context, destination AI instance, callback type/ID, raw function operand, source-resolved function key when unique, enclosing branch conditions, and matching Iris engine dispatch sites for literal IDs. Non-unique local assignments and branch alternatives are shown as uncertain operands. When a unique identity is available for both GAOs plus a literal ID and unique function key, JadeView lists source-reachable `AICBDel` sites with the exact same tuple `(destination, context, ID, function)`. Jaded `AIfunctions_ai.c:607-635` and Iris `ai_aifunctions.c:459-475` show deletion matching all three stored values and removing only the first matching entry. This source-level tuple match does not establish which call executes first or whether either call runs. Dynamic `AI_MainActor[...]` destinations are deliberately left unresolved.

Potential `AIReinitVars` calls appear in a separate **Potential AI instance reset sites** section. Jaded `AIfunctions_ai.c:746-761` and Iris `ai_aifunctions.c:533-546` show that the API resets the current GAO's own AI instance, not an explicit callback destination; the reset clears dynamic callback registrations (`AIengine.c:1444-1497` and Iris `ai_common.c:375-420`), except for the universe instance. JadeView does not associate a reset site with a registration unless the receiver identity can be independently resolved. Recognized current-owner identity-flag predicates are compared individually with serialized GAO flags, with an explicit warning that runtime changes and combined branch logic are not evaluated. A callsite does not prove it ran, that the destination AI instance was initialized, that the registration survived a reset/deletion, or that the corresponding engine phase executed. Exact runtime behavior still needs AI-instance state and branch/callback execution.

The production graph audit now serializes these findings per reachable owner. On `FF005833 / BF00218E`, it found 22 reachable `AICBAdd` and 4 `AICBDel` source candidates, but no pair with all four tuple identities uniquely resolved, and no reachable `AIReinitVars` site. In the inspected Add examples, the callback context resolves to the source owner while the destination is dynamic or null; those candidates remain unpaired by design. This result describes the decoded source graph only and does not establish whether runtime callbacks were registered or dispatched.

The five AI track callback slots are a separate route: Iris copies them into the live instance, then `AI_RunInstance` invokes the current slot when its delay expires; track-change operations can replace that slot. The UI reports the archived assignments, not the live slot or timer state.

The timeline now has a **Find script event owner, GAO, key, or command…** field near the top. It filters the lower **SceneEvents EVE inventory** by owner and event keys, channel index/target, decoded command name, or loaded command target; entering a query opens the matching inventory. The inventory is separated into **Clip-linked**, **Script owners**, and **All** tabs, so EVE lists attached to the selected clip can be inspected separately from independently gated owner lists. For example, search a GAO key/name or `OBJRotateLocalY` to find channels that affect a prop without manually opening every list. The result count is the number of matching lists, not commands or confirmed runtime activations.

For callback-driven `TRA*` calls, expand **Inspect addressed EVE channels** directly below the resolved call to see its channels and recognized commands in context. When a command target belongs to the assembled cinematic world, select its row to frame the object. The separate **SceneEvents EVE inventory** remains available for browsing all event lists. This is a navigation and inspection improvement; it does not run the scene's script VM.

The `TRA*` call inspection also evaluates a narrow, source-confirmed case: a direct `AI_EvalFunc_OBJ_FlagsIdentityTest_C` against the current owner and a literal flag mask. It compares that condition (including `!` and `else`) with the owner's serialized GAO flags and reports whether that branch matches the saved flags. For example, the pump object's `0x0800F060` flags do not contain `0x02000000`. This is only a saved-state hint: earlier callbacks or gameplay may change flags before the call, so it does not prove that a branch cannot run at runtime. Other predicates remain unevaluated.

Direct `OBJ_CapaTest` checks on the current owner are described separately: Iris tests whether any bit in the requested mask is currently set. JadeView reports the mask and leaves the branch result unknown because live capabilities are runtime state, not an OVA snapshot. This applies to resolved and unresolved `TRA*` calls alike, so it can clarify a gate even when the call's event-list receiver cannot be joined to a serialized `SceneEvents` record.

The `Cine_Events` inspector also evaluates its start capability test against a uniquely resolved actor's archive-loaded initial capability mask. Iris compares `(currentCapabilities & des_i_capa_test1)` with `des_i_capa_etat1 * des_i_capa_test1`; JadeView labels this as an initial snapshot pass/fail and does not use it to suppress or force playback. A prior script or saved game can change those capabilities before the callback, so the runtime result stays unconfirmed. Other start gates remain unknown when they depend on collisions, queued messages, activity, visibility, destructible state, or saved flags.

The timeline's **Script-owned EVE preview** lists other `SceneEvents` owners whose object and event list resolve in the cinematic world or its exact paired gameplay world. Owners remain disabled by default so conditional events are not mistaken for confirmed game playback. When the selected clip's resolved timeline writes satisfy the owner's encoded `Cine_Events` special-flag tests, the row offers **Preview from …s**; choosing it schedules that owner's serialized channels from the matching flag-write time, with a configured `Cine_Events` delay estimate when its effective `f_first_delay`, `des_f_tempo`, and zero `f_timecode` are known. The estimate is `max(signal time, f_first_delay) + des_f_tempo`; the tooltip distinguishes it from runtime truth. It does not claim that the owner really activated: actor activity, capabilities, priority, save state before the clip, callback dispatch cadence, and other runtime gates are still not simulated. When the selected clip has a decoded message or literal `MSGSendEx`/`MSGSendAll` whose queue, message ID and `Int1` mask match the configured start gate, the row also offers a **Message** time candidate at the first matching send and uses the same bounded delay estimate. Message queue capacity/lifetime/order, gate activation, or execution are not proven. Owners without a flag or message candidate retain the manual **Preview** switch from cinematic time zero. Synchronized GLB export uses the same preview selection and start offset. The nested EVE audit records available owners and source event keys. The owner switch also governs `RunningInit` channels: they do not bypass the disabled-by-default preview switch just because the serialized EVE flag says they run when that owner initializes.

This follows the engine implementation in Iris and Jaded: `EVE_ReinitTrack` initializes a track's runtime Running bit from `EVE_C_Track_RunningInit`, while `EVE_SetRunningTrack(s)` changes runtime state and resets time/event position when starting a stopped track. The serialized flag therefore describes what happens when an EVE owner is initialized; it does not prove that every loaded world owner was initialized or passed its `Cine_Events` gates. JadeView auto-previews source-reachable callback tracks it can resolve and unclassified `RunningInit` lists in the selected world. Script-owned lists with a preview switch are withheld until selected, so toggling an owner off also removes its `RunningInit` channels. Runtime start gates remain unknown.

This automatic EVE path does not evaluate owner callback gates or runtime state. It evaluates `OBJ_OrientTo` for uniquely resolved non-actor objects: each command snaps the object's local -Y sight axis toward the referenced object's position using the source engine's +Z banking vector, while preserving position. It also evaluates `OBJRotateLocalY` from its serialized float angle and EVE key duration. Iris/Jaded source confirms each key's angle is the total local-Y increment for that event; the preview distributes it over the event's active frames, uses the shared EVE clock for pause, stop, restart and looping, and rebuilds the pose from source time on every seek. Both operations are sampled into synchronized-scene GLB export. The elevator route `35009EF6` now exercises this generic path for `1_1_obj_verin_axe.gao` without a name-specific rule. A serialized `RunningInit` bit is only applied when the EVE owner is initialized: Jaded's loader calls `EVE_ReinitData`, which marks those runtime tracks running. JadeView seeds such tracks at clip time zero only for owners without an explicit script-owner preview control; a controlled owner's `Preview` switch is authoritative. The nested transform clock reads `AutoLoop` / `AutoStop`: loop tracks wrap local time, auto-stop tracks become stopped at the final key, and tracks with neither flag hold their final pose while remaining running. Source-confirmed `TRAStop`, `TRAPause`, `TRAUnPause`, `TRAPlay`, `TRASetEnd`, `TRASetTime`, `TRAReinit` and `TRAReinitAll` semantics share that clock: stop holds the cursor, pause freezes it, unpause resumes it, and a play request on a running track is a no-op. `TRAPlay` restarts a stopped auto-stop track from zero; `TRASetEnd` seeks the selected running track to its final decoded local time; `TRASetTime` seeks every EVE channel on the target while preserving run/pause state and, past the list end, clamps the cursor to the last event's start. Its 16-bit frame cursor has a representable unwrapped range up to 65535/60 seconds; seeks beyond that are left unresolved instead of guessing how the engine's wrap interacts with track events. `TRAReinit` resets the selected track time and event cursor, clears pause/done state, and restores its serialized `RunningInit` bit; `TRAReinitAll` applies that reset to every track in the owner EVE list. Iris's event-track functions and `events.c`, plus Jaded's `AIfunctions_tra.c` and `EVEplay.c`, confirm these cursor and state rules. JadeView models the supported cursor effects in the shared playback/export clock. Runtime object-processing state, callback gates, callback scheduling and actual VM execution are still not evaluated; callback-bound channels remain timeline overlays based on serialized owner links and reachable source calls, not proof that the game passed the owner's gates or executed the callback.

Source review narrows the command timing and hierarchy semantics for EVE playback. Iris `TRAPlay_C` calls `EVE_SetRunningTrack`; Jaded resets the event cursor/time and clears pause/done bits only when transitioning a stopped track to running, so a play request on an already-running channel does not restart it. Iris `OBJRotateLocalY_C` applies an incremental local-axis rotation and, while EVE is running, scales the supplied angle by `EVE_gf_DT / (event duration / 60)`; Jaded expresses the same ratio as current event delta divided by that event's frame duration. The serialized angle is the total increment for that EVE key, not a constant angular velocity. JadeView uses the shared EVE clock for pause, stop, restart, and loop mapping, then samples the cumulative local-Y pose for preview and GLB export.

Iris `OBJ_OrientTo_C` aims from the source object's absolute position toward the reference object's absolute position using world-up +Z, then recomputes local orientation for hierarchy children while preserving their current local position. ### Callback action-slot links

The cinematic script inspector joins source-reachable `ACTActionSet`, `ACTActionFrameSet`, and `ACTActionFrequencySet` calls to the same owner's decoded action table. `ACTActionSet` resets the action clock; `ACTActionFrameSet` selects the action with forced transition semantics and restores its `int16` frame value; `ACTActionFrequencySet` selects with forced semantics and applies the source's `60/64` frequency conversion. These behaviors are implemented in `external/irisEng/ai/ai_actionfunctions.c`; action-slot validation and negative forced-ID normalization are in `external/irisEng/actions.c`. The inspector retains the callback path, source location, branch predicates and any uniquely resolved OVA scalar. It lists the matched clip/shape resources but does not claim that the branch passed, the callback ran, or that the selected animation is currently active.

The join is exercised by synthetic fixtures for all three APIs, including the `_CURRENT` and explicit-target signatures, negative forced action IDs, action-table misses, and dynamic frequency values that must remain unresolved. The production graph audits for `FF005833 / BF00218E`, `FF0045A2 / 3500B8EA`, and `FF00791B / BF003BD1` each resolve source-reachable `ACTActionSet` requests to owner action tables (255, 344, and 255 rows respectively, including source-world participant owners); these sampled callback graphs contain no resolvable `ACTActionFrameSet` or `ACTActionFrequencySet` requests. The newly supported frame/frequency variants are therefore source-verified and fixture-tested, but not yet demonstrated in those three cinematic callback graphs. These records are possible callback requests, distinct from timed EVE commands and from live game state.

Serialized cinematic `ACTActionSet` events now also decode the high-bit force marker before validating the action-table slot. Iris's `ACT_SetAction` masks `0x80000000` from a negative action ID, bypassing the same-running-action early return; Jaded's `ACT_SetAction` documents the same bit as forcing the action even when it is already active. The preview consequently treats `0x80000000 | slot` as a forced restart of `slot`, while preserving `0xFFFFFFFF` as the no-action sentinel. A regression fixture checks both encodings. An archive-wide scan of the current cinematic action requests found no uses of this encoded form, so this is source-backed format coverage rather than a claimed fix for a specific scene. Jaded also documents `0x40000000` (disable blending) and `0x20000000` (reinitialize animation data); those extra flags are not applied because the Iris implementation recovered for BGE does not confirm them.

Serialized event-resource commands now have a separate link: their target GAO and literal action slot are joined to that target's decoded action table, then to clip and shape keys. This covers the common timeline-authored `ACTActionSet`, `ACTActionFrameSet`, and `ACTActionFrequencySet` forms without relying on callback C call sites. On the audited worlds, this resolved 40 command rows for `FF005833 / BF00218E` (32 `ACTActionSet`, 7 frame-set, 1 frequency-set), 169 for `FF0045A2 / 3500B8EA` (136, 32, 1), and 7 `ACTActionSet` rows for `FF00791B / BF003BD1`. Those counts cover linked owner event resources in each selected cinematic world, not only commands executed by the selected cinematic or a running game. The BF003BD1 sample contains no frame/frequency action command. A missing target action kit or slot and a command with a missing control value stay unresolved. This is a configured event command and a resource match; it does not establish that the enclosing callback started the event track or that the game executed the command.

The selected cinematic's own timeline commands use a time-scoped action-kit resolver. Before each action request, it applies earlier literal `ACTKitMerge` and `ACTKitMergeOver` commands for that target, then resolves the requested slot and retains the world that supplied that slot. Iris `actions.c` confirms that `ACTKitMerge` copies only non-null source slots without replacing existing destination actions; `ACTKitMergeOver` replaces every slot in range and clears destination slots where the source kit has no action. A reversed range copies nothing. This fixed a real false-unresolved case: in `BF00218E`, `Cine_PNJ_Secundo.gao` merges slots 1–50 from `BF003ABE` at time 0, selects slot 10 at 8.57s and slot 11 at 44.70s; both now resolve to the `BF000127` source-world kit. This is a structural, timeline-ordered join over literal commands; callback-driven merges and gameplay gates are not executed, so it does not claim that the game dispatched those actions.

In particular, Iris PC mode 8 is an unnamed effect and mode 9 is color balance, while Jaded's Xenon enum labels mode 8 brightness and mode 9 contrast; the catalog preserves this platform difference instead of assigning the Xenon names to PC. Both call forms change global post-processing state, not a target mesh. JadeView evaluates PC modes 8 and 9 from the cinematic playhead. Below 0.5 Iris blends the source with RGB 128 using vertex diffuse alpha `floor(510p)/255`. Above 0.5 its three texture stages perform `MODULATE(texture, diffuse)`, `ADD(texture, current)`, then `SUBTRACT(current, texture-factor)`, with packed factors `floor(255(2p-1))` and `floor(128(2p-1))`; the preview applies the corresponding contrast formula and clamps the final color. The neutral value 0.5 bypasses the pass. This models the recovered PC formula, though Direct3D fixed-function intermediate precision and render-target format are not duplicated exactly by the OpenGL preview. PC mode 8 applies a quantized additive/subtractive RGB offset around neutral 0.5 before mode 9, matching Iris texture-factor ADD/SUBTRACT; the effect name itself remains unidentified. Other AE modes remain inspector-only. ### Companion status messages (type 49)

The message inspector now decodes type 49 only for script owners whose assigned callback graph reaches Iris's `companion_co_exec_get_message` handler. Iris uses this message to update a companion's requested status, optional action, placement, facing direction, and world in the shared companion table, then selects a companion mode. `Int1=3` also writes the collision-start matrix from `Vector1`; `Int1=4` defers `Int2` as an action instead of immediately calling `ACTActionSet`. Zero vectors and `Float2=0` select the receiver's current position, sight, and world. The source also skips unchanged status/world updates (except status 3) and defers application in modes 9 and 17.

This is deliberately callback-scoped: Iris also assigns other meanings to type 49 for unrelated script families (including Crochax scale, aircraft mode, and SFX lighting), so JadeView must not label every numeric type-49 message as a companion command. In the UI, inspect the typed messages under **Cinematic Timeline** or expand a serialized **SceneEvents** channel; the explanation includes the resolved EVE execution owner and callback path. The values are static message data and source behavior, not proof the callback ran, a runtime branch passed, or an actor appeared in-game. Before applying a companion MSG 49, Iris requires status 3, a changed `old_companion_status`, or a nonzero `f2` different from the stored world ID. It then defers processing while `co_current_mode` is 9 or 17 and requeues the message. BF snapshots do not reconstruct those live values. JadeView therefore keeps recognized non-status-4 action requests useful for preview but labels their message-time application as approximate and reports the unresolved status/mode gates. Jaded independently documents an engine-level sub-frame gate in `ACTcompute.c:673-686`: `ACT_SetAction` requested during EVE is applied after the current frame's elapsed portion is rendered. That generic Jaded timing rule does not replace the Iris companion-message gates. Regression checks cover callback scoping, candidate body-action preview, and unresolved timing gates.

### World activation versus AI callback execution

The selected owner's **World AI callback scheduling** evidence now reports the two engine gates separately. A serialized status bit `0x40000000` maps to runtime `flags2 0x00400000`; Iris rejects ordinary-time activation when `flags2 & 0x04400000` is nonzero, so this serialized bit is a confirmed ordinary-activation blocker at load unless runtime state changes. During nonzero `ENG_gf_SpecialTime`, the alternate activation path instead requires `flags2 0x04000000`, and JadeView reports whether the serialized initial word contains that bit. After activation, `AI_MainCall` skips invalid or already-processed entries, optionally requires distance when `extended->extraFlag & 0x4` is set, redirects processing through unprocessed hierarchy parents, requires an allocated `AIInstance`, and skips `AI_RunInstance` while runtime `flags2 0x00400000` remains set.

These are ordered source-derived eligibility checks, not a claim that a callback ran: the BF snapshot cannot show later flag mutations, special-time state, table membership, distance, hierarchy changes, instance allocation, or callback results. The mapping is from retail Iris `gameobject.c` (GAO state load and `OBJ_UpdateStatusFlagRTL`), `world.c` (`WOR_ActivateObjectIfFlagsAllow` and EOT construction), and `ai_common.c` (`AI_MainCall`).

Saved-flag identifiers resolved through callback-local variables are now causal with respect to the indexed source call: only a unique assignment at or before that call line may supply the flag number. Later assignments are ignored, and a non-unique assignment stays unresolved. This prevents a later write in the function from being mistaken for the value used by an earlier trigger/test; it does not attempt general C data-flow or path-sensitive alias analysis.
